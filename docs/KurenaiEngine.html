1. アーキテクチャ

KurenaiEngineは 3つのDLLに分かれてビルドされます。 KurenaiEngineLibrary.dll(共通基盤。RHI抽象化層・Window・Camera・ モデル/シーン読み込みと、3D/2D共通の土台KurenaiEngineBaseを公開)、 KurenaiEngine3D.dll、KurenaiEngine2D.dllで、3D/2Dはいずれも KurenaiEngineLibraryにのみ依存し、互いには依存しません。 

KurenaiEngine/
  KurenaiEngineLibrary.vcxproj  ← 共通基盤(DynamicLibrary)
  KurenaiEngine3D.vcxproj       ← 3D API(DynamicLibrary)。Libraryにのみ依存
  KurenaiEngine2D.vcxproj       ← 2D API(DynamicLibrary)。Libraryにのみ依存
  Source/
    Engine/    ← 公開API(このドキュメントで説明する全て)
      KurenaiTypes.h        GraphicsAPI enum, DLLごとのエクスポートマクロ
      KurenaiEngineBase.h   3D/2D共通の土台(非公開コンストラクタ。KurenaiEngineLibraryが公開)
      KurenaiEngine3D.h     3Dサンプル向け公開クラス(KurenaiEngine3Dが公開)
      KurenaiEngine2D.h     2Dサンプル向け公開クラス(KurenaiEngine2Dが公開)
    Library/   ← 低レベルAPI(RHI抽象化層、Window、Camera、モデル読み込みなど。4章参照。KurenaiEngineLibraryが公開)
      RHI/ Core/ Assets/
  Shaders/3D/  ← KurenaiEngine3Dが内部で使うHLSLシェーダ一式
  Shaders/2D/  ← KurenaiEngine2Dが内部で使うHLSL(Sprite2D.hlsl)

Source/Engine/ と Source/Library/ はどちらも公開APIで、 どちらのクラス・関数も対応するDLLから __declspec(dllexport) されています (Source/Library/RHI/DX11, DX12 配下のバックエンド実装クラス自体は 非公開で、RHI::IRHIDevice などのインタフェース越しにのみ利用します)。 用途に応じて使い分けてください。

  • まず動かしたい・定番の3D/2D表現で十分な場合 → KurenaiEngine3D / KurenaiEngine2D(2章・3章)
  • 独自の描画パイプラインを組みたい場合(カスタムシェーダ、独自のポストエフェクト、 スプライト以外の2D表現など) → Library の低レベルAPI(4章)を直接利用

サンプルプログラムを新規に作成する場合、プロジェクトのインクルードディレクトリには KurenaiEngine/Source/Engine を追加し(KurenaiEngine3D.h などを includeするため)、KurenaiEngineLibrary.vcxproj と、使う方(KurenaiEngine3D.vcxproj または KurenaiEngine2D.vcxproj)の2つへプロジェクト参照を張ってください (Samples/Sample3D, Samples/Sample2D の .vcxproj を 参考にできます。DLLを経由したプロジェクト参照は推移的にリンクされないため、Libraryへの参照は 省略できません)。Library の低レベルAPIも使う場合は KurenaiEngine/Source/Library もインクルードディレクトリに追加してください (RHI/IRHIDevice.h のように Library を起点とした相対パスでincludeする)。 実行ファイルの出力先はビルドの度に各DLLが生成される場所(リポジトリ直下の Build\Bin\<Platform>\<Configuration>\<プロジェクト名>\)と揃えてください。 DLLは実行ファイルと同じフォルダに置かれていないと起動時に読み込めません。

2. Kurenai::KurenaiEngine3D — 3Dサンプル向け公開API完結型

KurenaiEngine3D は、Deferred Shading(G-Buffer: Albedo/Normal/Metallic-Roughness+ 深度)によるPBRレンダリング、平行光の影(カスケードシャドウマップまたはレイトレーシング)、 IBL(環境光)、DDGI(プローブ格子による位置ごとの拡散グローバルイルミネーション)、 AO/間接光(SSAO/SSILまたはレイトレーシング)、鏡面反射(スクリーンスペース(SSR)またはレイトレーシング)、 複数シーンの切り替え、ImGuiによる設定パネル一式までを内包した完結型の3Dレンダラーです。 構築して Run() を呼ぶだけでウィンドウが開き、ユーザーが閉じるまでブロックします。 

#include "KurenaiEngine3D.h"
#include "KurenaiTypes.h"

int WINAPI wWinMain(HINSTANCE, HINSTANCE, LPWSTR, int)
{
    CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED); // WICテクスチャ読み込みに必要

    // 実行中にグラフィックスAPIを切り替えたい場合は2.1節のループ形にする
    Kurenai::KurenaiEngine3D engine(Kurenai::GraphicsAPI::DX11); // またはDX12
    engine.Run();

    CoUninitialize();
    return 0;
}
namespace Kurenai
{
    class KurenaiEngine3D : public KurenaiEngineBase
    {
    public:
        explicit KurenaiEngine3D(
            GraphicsAPI api = GraphicsAPI::DX11,
            uint32_t renderWidth = Defaults::RenderWidth,    // 1280
            uint32_t renderHeight = Defaults::RenderHeight,  // 720
            size_t initialSceneIndex = 0);
        ~KurenaiEngine3D();
        void Run();

        // グラフィックスAPIの実行時切り替え(下記参照)
        bool HasPendingGraphicsAPIChange() const;
        GraphicsAPI GetPendingGraphicsAPI() const;
        uint32_t GetRenderWidth() const;
        uint32_t GetRenderHeight() const;
        size_t GetCurrentSceneIndex() const;
    };
}
  • renderWidth/renderHeight はG-Bufferなどの内部レンダリング解像度 (ウィンドウサイズとは独立)。ウィンドウは常に1280x720で開始し、リサイズ可能。表示時はアスペクト比を 保ってレターボックス/ピラーボックス表示される。実行時に「システム」パネルからも変更できる。
  • initialSceneIndex は起動時に読み込むシーンの番号 (Assets/Scenes/*.ksceneをファイル名の昇順に並べたときの位置。範囲外なら0へフォールバック)。 グラフィックスAPIを切り替える際に、同じシーンで作り直すために使う。
  • Run() を呼ぶと以下を自動的に行う(設定変更やシーン読み込みはすべて ImGuiパネル経由):
    • WASD で移動、E/Q で上下移動、Shift で高速移動
    • 右クリックを押しながらマウス移動でカメラ回転
    • F1 でImGuiパネルの表示/非表示切り替え
    • 8つのImGuiパネル(シーン / レンダリング / ポストプロセス / ライティング / 反射プローブ / デバッグ表示 / システム / プロファイラ)で表示アセットの切り替え、AO/間接光・ スクリーンスペースシャドウ・タイルドライトカリングのON・OFFやパラメータ調整、 AO/間接光の手法(SSAO / SSIL / レイトレーシング)・平行光の影の手法 (なし / カスケードシャドウマップ / レイトレーシング)・ 反射の手法(なし / スクリーンスペース / レイトレーシング)の切り替え、 トーンマップ・TAA・ブルーム・自動露出の調整、デバッグ表示バッファの選択、 時刻(昼夜サイクル)・月の位置・手続き空・EV100(露出)の調整、 ポイント/スポットライトの一覧・追加・複製・削除・編集、反射プローブの編集と焼き直し、 FPS/CPU/GPUの計測値確認ができる。パネルはドッキングに対応しており、配置とサイズは 実行ファイルと同じフォルダのimgui.iniへ自動保存される
    • ウィンドウの位置・サイズ・最大化状態は終了時に実行ファイルと同じフォルダの window.iniへ保存され、次回起動時に復元される (window.iniを削除すると既定のサイズで起動する)
  • 表示できるシーンはビルド済みバイナリに組み込み済み(Sponza / Bistro (McGuire) Exterior / Bistro (McGuire) Interior / White Furnace Test / Material Test / Light Test / Reflection Probe Test)。カスタムモデルの追加や、 シーン一覧の外部からのカスタマイズは現状の公開APIではサポートしていない(Run() を 呼ぶ以外のカスタマイズ余地がないのが KurenaiEngine3D の設計上の割り切り)。
  • コンストラクタに渡した GraphicsAPI に応じてDX11/DX12いずれかのバックエンドで 動作する。実行中に「システム」パネルからAPIを切り替えられる(下記)。

2.1 グラフィックスAPIの実行時切り替え

「システム」パネルでグラフィックスAPIを変更すると、Run() はウィンドウを閉じずに 戻ります。呼び出し側はこのオブジェクトを破棄し、新しいAPIで作り直してください (デバイスに紐づくリソースをすべて作り直す必要があるため、オブジェクトごと作り直す方式です)。 

Kurenai::GraphicsAPI api = Kurenai::GraphicsAPI::DX11;
uint32_t renderWidth = Kurenai::Defaults::RenderWidth;
uint32_t renderHeight = Kurenai::Defaults::RenderHeight;
size_t sceneIndex = 0;

for (;;)
{
    Kurenai::KurenaiEngine3D engine(api, renderWidth, renderHeight, sceneIndex);
    engine.Run();

    if (!engine.HasPendingGraphicsAPIChange())
    {
        break; // ウィンドウが閉じられた
    }

    // 作り直しても保ちたい状態を引き継ぐ
    api = engine.GetPendingGraphicsAPI();
    renderWidth = engine.GetRenderWidth();
    renderHeight = engine.GetRenderHeight();
    sceneIndex = engine.GetCurrentSceneIndex();
}
  • ウィンドウは作り直されますが、位置・サイズは window.ini を介して復元されます。
  • 引き継がれるのは上記3つ(API・内部レンダー解像度・シーン)だけです。 AO・シャドウ・IBL・ポストプロセスなどの設定は新しいインスタンスで既定値へ戻ります。
  • ログの出力先も切り替わります(KurenaiEngine_DX11.log ⇔ KurenaiEngine_DX12.log)。同じAPIへ戻ったときは前半のログを消さずに追記します。
  • この分岐を実装しない(Run() を1回呼ぶだけの)アプリケーションでは、 APIを切り替えるとRun()が戻ってそのまま終了します。

3. Kurenai::KurenaiEngine2D — 2Dサンプル向け公開API軽量API

3.1 座標系

ワールド座標=ウィンドウのピクセル座標(原点は画面左下、Y-upの標準的な2Dゲーム座標系)。 DrawSprite の x, y はスプライト中心の位置、width, height は ピクセル単位のサイズ、rotationRadians は画面奥から手前を見た反時計回りのZ軸回転。

3.2 カメラと論理解像度

カメラ系のAPIを一度も呼ばなければ従来どおり「クライアント領域を過不足なく映す」 状態になります(ワールド座標0〜幅・0〜高さがそのまま画面いっぱいに出て、ウィンドウの リサイズにも自動追従する)。反映はBeginFrame()の時点なので、設定は BeginFrame()より前に行ってください(フレーム途中の変更は次のフレームから効きます)。

状態ウィンドウをリサイズしたとき
何も設定していない(既定)カメラ中心が新しいクライアント中央へ追従し、ワールド0〜幅・0〜高さが常に映る
SetCameraPosition済みカメラ中心は固定。見えるワールドの範囲は「クライアントサイズ÷ズーム」なので、ウィンドウを広げると見える範囲が広がる
SetVirtualResolution済み見えるワールドの範囲は「論理解像度÷ズーム」でウィンドウサイズに依存しない。ビューポートだけが拡縮する
  • SetCameraZoomは1.0で等倍、2.0で2倍に拡大表示(= 見えるワールドの範囲が1/2)。 0以下・NaNはログを出して無視する。
  • SetVirtualResolution(w, h)は、ワールド座標0〜w・0〜hの範囲がアスペクト比を 保ったままクライアント領域の中央へ収まるようスケール＋センタリングする。 「1600x900で組んだ盤面を、どのウィンドウサイズでも同じ構図で見せる」用途に使う。 (0, 0)を渡すと解除される(このときsnapToIntegerScaleも落ちる)。
  • 第3引数snapToIntegerScale=trueにすると、拡大率をfloorして 整数倍へ落とし、ビューポートの原点も整数へ丸める。これにより論理解像度の 1テクセルが画面の整数個の画素へ正確に対応する(ドット絵の整数倍拡大に必要。 詳細は3.3節)。余った分はレターボックス/ピラーボックスの余白へ回るため、 既定の実数倍より表示は一段小さくなる。 クライアント領域が論理解像度より小さい場合は整数倍が取れないため、 スナップせず実数倍へフォールバックする(最初の1回だけログに残す)。
  • 余る側にはレターボックス/ピラーボックスが出る。この余白はビューポートの外なので、 そこへ向けて描いたものは投影のクリップで消える(余白の色はBeginFrameの クリア色になる。黒帯にしたい場合はBeginFrame(0, 0, 0)を渡す)。
  • ClientToWorld / WorldToClient / GetMouseWorldPosition は クライアント座標(GetClientMousePositionが返す、原点は左上・Y-down)と ワールド座標を相互変換する。カメラ位置・ズーム・レターボックスをすべて考慮するので、 マウスの当たり判定は必ずこれを通すこと(これらを使わずに height - yで変換すると、ズームや論理解像度を使った瞬間にずれる)。

3.3 スプライトのサンプリングとドット絵

SetSpriteFilter / SetSpriteAddressMode は描画状態として 保持され、以後の DrawSprite / DrawSpriteUV / DrawLine に適用されます (呼び出しごとに指定する必要はなく、フレームの途中で何度でも切り替えられます)。 DrawCircle / DrawRoundedRect / DrawPolyline はテクスチャを 読まないため影響を受けず、DrawText は常に専用の Linear + Clamp サンプラーを 使います(フォントアトラスを点サンプリングにするとアンチエイリアスが崩れて文字が汚れるため、 SetSpriteFilter(Point) にしていても文字だけは元のまま描かれます)。

値意味
SpriteFilter::Anisotropic(既定)異方性フィルタリング16x。ミップ付きテクスチャにしか効かない — LoadTextureで読んだPNG/BMP等はミップが生成されるので効くが、CreateSolidColorTexture・フォントアトラス・.tga/.ddsはミップ1枚なのでLinearと同じ結果になる
SpriteFilter::Linearバイリニア補間
SpriteFilter::Point最近傍(点)サンプリング。ドット絵向け
SpriteAddressMode::Wrap(既定)UVを繰り返す。タイリングするスプライト向け
SpriteAddressMode::Clamp端のテクセルを引き伸ばす。アトラスの区画をDrawSpriteUVで切り出す場合はこちら

ドット絵を滲ませずに拡大するのに必要な3点

どれか1つでも欠けると輪郭が滲みます。3つは互いに代用できません。

  1. SetSpriteFilter(SpriteFilter::Point) — 補間そのものを止める。これだけでは足りない。
  2. SetSpriteAddressMode(SpriteAddressMode::Clamp) — Wrapのままだと、スプライトの外周でフィルタのタップが テクスチャの反対側の端へ回り込む。実測では、左端に赤・右端に青を置いた 32x32のスプライトをLinear+Wrapで描くと、左端の色が 純赤(232, 48, 56)から紫(146, 78, 138)へ引きずられた (Clampでは純赤のまま。docs/ImplementationDetail.md参照)。
  3. SetVirtualResolution(w, h, true) — 拡大率が実数だとテクセル中心が画素中心からずれる。 1280x720のウィンドウへ論理解像度240x135を収めると拡大率は5.333倍で、 このとき点サンプリングにしても1テクセルが5画素と6画素に割れる (実測: 4テクセル角のチェッカーの1マスが21画素と22画素に交互に割れた。 スナップONでは全マスがきっかり20画素)。

SetCameraZoomと併用する場合、画面上の総拡大率は 「整数倍 × ズーム倍率」になります。ズームに整数以外を指定すると 総拡大率が実数へ戻るため、ドット絵では整数のズームを使ってください。 スプライトの中心座標とサイズも整数にしておくこと(0.5刻みの中心だと スプライトの端がテクセル境界に乗らず、スナップが効いていても輪郭がずれます)。

ドット絵の画像形式は .tga / .dds にする

LoadTexture はWIC経由で読む画像(PNG/BMP/JPEG等)に対して ミップマップ生成とBC7圧縮を行います。BC7は4x4ブロック単位の非可逆圧縮なので、 色数の少ないドット絵では色が僅かにずれます。 .tga と .dds だけは「既に圧縮・ミップ済みの配布形式」として 素通しされるため、無圧縮・ミップ無しのまま届きます。 ドット絵はこちらの形式で用意してください (輪郭の位置はどちらでも保たれますが、色を原画どおりにしたい場合は素通しの経路が要ります)。

3.4 使い方

#include "KurenaiEngine2D.h"
#include "KurenaiTypes.h"

using namespace Kurenai;

int WINAPI wWinMain(HINSTANCE, HINSTANCE, LPWSTR, int)
{
    CoInitializeEx(nullptr, COINIT_APARTMENTTHREADED);

    KurenaiEngine2D renderer(L"My 2D Game", 1280, 720, GraphicsAPI::DX11);

    TextureHandle playerTexture = renderer.LoadTexture(L"Assets/player.png", false);
    float x = 640.0f, y = 360.0f;

    while (!renderer.ShouldClose())
    {
        renderer.PumpEvents();
        if (GetAsyncKeyState(VK_ESCAPE) & 0x8000)
        {
            renderer.Close();
        }

        // 入力処理・座標更新はアプリケーション側の責任(WinAPIを直接使う。5章参照)
        if (GetAsyncKeyState('D') & 0x8000) x += 4.0f;
        if (GetAsyncKeyState('A') & 0x8000) x -= 4.0f;

        renderer.BeginFrame(0.1f, 0.1f, 0.15f);
        renderer.DrawSprite(x, y, 64.0f, 64.0f, 0.0f, playerTexture, 1.0f, 1.0f, 1.0f, 1.0f);
        renderer.EndFrame(true);
    }

    CoUninitialize();
    return 0;
}
  • LoadTexture / CreateSolidColorTexture はロード時にまとめて呼び、 返ってきた TextureHandle を保持しておいて毎フレームの DrawSprite に 渡す(KurenaiEngine2D が内部でテクスチャの実体を所有し続けるため、 renderer が生存している間は有効)。
  • DrawSprite の r, g, b, a はテクスチャに乗算されるティント色。 a < 1.0 で半透明合成される(常にアルファブレンド有効。深度テストは行わないため、 重なり順は呼び出し順で決まる — 先に呼んだスプライトほど背面に描かれる)。
  • DrawSpriteUVはDrawSpriteの「テクスチャの一部だけを描く」版。 srcU0, srcV0, srcU1, srcV1は0.0〜1.0の正規化UVで、原点は左上・V下向き (テクスチャの標準的な向き)。DrawSpriteはこれを (0, 0)-(1, 1)で呼ぶだけの実装になっている。
    アイコン類を1枚のアトラスへまとめ、LoadTextureの回数とフレーム中のテクスチャ 切り替え回数を減らす用途に使う。区画をピクセルで管理する場合は GetTextureSizeでテクスチャのピクセルサイズを取り、 ピクセル座標 / サイズで正規化UVを求める。
    アトラスを作るときは、区画の周囲に1px以上の余白を入れること。 2Dのサンプラーは繰り返し(Wrap)+異方性フィルタなので、区画をぴったり詰めると 縮小表示時に隣の区画の色がにじむ。
  • BeginFrame/EndFrame は1フレームにつき必ず1回ずつ呼ぶ。 DrawSprite/DrawSpriteUV/DrawCircle/DrawLine/DrawRoundedRectはその間に好きな回数呼べる (DrawPolylineだけは1フレームあたりの本数に上限がある。下記)。
  • DrawCircleは中心(x, y)・半径radiusの塗り円をふちのアンチエイリアス付きで描画する (テクスチャ不要、ピクセルシェーダーの距離場でマスクする)。DrawLineは (x1, y1)-(x2, y2)を結ぶ太さthicknessの線分を、内部的には 回転・拡縮した矩形としてDrawSpriteと同じパイプラインで描画する。いずれも r, g, b, aは塗りつぶし色で半透明可。
    DrawCircleはDrawRoundedRectと同じ形の枠線引数を持つ。 塗りをa = 0にして枠線だけを指定すると、中が完全に透明なリングになる (射程円・範囲表示のように、下の描画を隠したくない用途向け)。
  • DrawPolylineは{x0, y0, x1, y1, ...}の順に並べた点列を、太さ thicknessの1本の帯として描く。角の接合はマイター(鋭角時はベベルへ フォールバック)、端は切りっぱなし(バットキャップ)。
    DrawLineを繋いで折れ線を描くと角の外側に扇形の隙間が空くが、これは点列をまとめて 1つのジオメトリ(重なりの無い三角形の集まり)として描くため隙間ができない。また各画素が きっかり1回だけブレンドされるので、半透明でも接合部の色が濃くならない。
    制限は次のとおり。
    • 折れ線が自分自身と交差する場合、その交点だけは2回ブレンドされる (1パスのアルファブレンドでは原理的に解決できない)
    • 1本あたり1024点まで。超えるとログを出して先頭1024点へ切り詰める
    • 1フレームあたり32本まで。超えるとログを出してその呼び出しを描画しない (DX12のステージングリングの段数で決まる上限。上限に達する前に弾くことで、 リングを周回して描画結果が静かに壊れるのを防いでいる)
  • DrawRoundedRectは中心(x, y)、サイズwidth x height、 角丸半径cornerRadiusPixels(ピクセル単位)の角丸矩形を、DrawCircleと同様 テクスチャ不要のピクセルシェーダー距離場(SDF)でふちをアンチエイリアスしながら描画する。 borderThicknessPixelsを0より大きくすると、塗りの内側にborderR/G/B/Aの 枠線をさらに重ねて描画する(既定は枠線なし)。UIのボタンやパネル背景など、角丸+枠線を 1回の描画コマンドで表現したい場合に使う。
    枠線は塗りとは独立したレイヤーとして、塗りの上へ通常のアルファ合成で重ねる。 このため塗りが半透明・完全透明でも枠線はその不透明度のまま出る(塗りが不透明な場合の 結果は変わらない)。DrawCircleの枠線もまったく同じ扱い。
    rotationRadiansはDrawSpriteと同じZ軸回転で、中心(x, y)まわりに回る。 width/heightと角丸半径・枠線太さは回転前のローカル空間での値 なので、回しても角丸や枠線の太さは変わらない。既定値0のため、回転を使わない既存の呼び出しは 従来どおり。
    なおDrawCircleには回転引数が無い(円は回しても見た目が変わらないため)。
  • DrawTextは既定(align = TextAlign::Center, verticalAlign = TextVerticalAlign::Middle) では(x, y)をテキスト中央基準としてtextを描画する。fontSizeは おおよその文字高さ(ピクセル単位)。コンストラクタ内でGDI(Yu Gothic UI)によりASCII印字可能文字 (0x20〜0x7E)一式をビットマップフォントとしてラスタライズしたテクスチャアトラスを 生成し、1文字ごとにアトラス内の該当矩形をサンプルするテクスチャ付き矩形として描画する (頂点シェーダーでUVをオフセット・スケールする点以外はDrawSpriteと同じパイプラインを使う)。 厳密なフォントレンダリング(ヒンティング等)は行わないため、HUD表示程度の可読性を想定している。
  • bold = trueを指定すると、通常とは別に構築される太字(FW_BOLD)アトラスを 使って描画する(通常版と太字版は別テクスチャ・別文字集合として独立に管理され、コンストラクタで 両方ともASCII一式が事前構築される)。
  • align(TextAlign::Left/Center(既定)/Right)でxの意味が変わり、 verticalAlign(TextVerticalAlign::Bottom/Middle(既定)/Top)でyの意味が変わる。 既定のまま(align = Center, verticalAlign = Middle)ならボタンの中心座標を そのまま渡すだけで正確に中央揃えできる。align = Center/Rightまたは verticalAlign = Middle/Bottomの場合、内部でMeasureText相当の幅・高さ計測を 行ってから描画開始位置を決めるため、呼び出し側で幅・高さを計算する必要はない (align = LeftかつverticalAlign = Topの組み合わせのみ、計測なしで(x, y)を そのままテキスト左上基準として使う、最も低コストな経路になっている)。
  • MeasureText(text, fontSize, bold)は指定した文字列・サイズ・太さで描画した場合の 実測済み幅(ピクセル単位、各グリフのAdvancePixelsの合計)を返す。DrawTextと同様、 アトラス未収録の文字はその場では幅0として扱われ、次のBeginFrame()でアトラスに追加された 以降は正しい幅が返る。ボタン幅の自動計算など、中央揃え以外の用途で幅そのものが必要な場合に使う。 改行は解釈しないため、複数行の文字列にはMeasureTextBlockを使う。
  • DrawTextはtextに含まれる'\n'で改行する ("\r\n"の'\r'は読み飛ばす)。2行目以降はGetLineHeightぶん下へ送られる。 alignは行ごとに適用され(Centerなら行ごとの中央揃え)、 verticalAlignはテキストブロック全体に対して適用される。
    指定幅での自動折り返しは行わない。折り返しが要る場合は、呼び出し側が MeasureTextで折り返し位置を決め、'\n'を挿入した文字列を渡す。
  • PushClipRect / PopClipRectは、以後の描画を矩形の内側だけに制限する (内部的にはシザー矩形)。スクロールするUIパネルのように、パネルからはみ出した項目を 切り落とす用途に使う。x, yは矩形の中心で、 DrawSprite/DrawRoundedRectとまったく同じ引数の意味なので、 パネルをDrawRoundedRectで描いた直後に同じ引数でPushClipRectすれば その内側へ子要素を閉じ込められる。
    ネストした場合は現在の矩形との積が有効になる(積が空なら対応する PopClipRectまでの描画は1ピクセルも出ない)。カメラ位置・ズーム・論理解像度による レターボックスはすべて考慮される。クリップできるのは軸平行な矩形のみで、 回転や角丸には追従しない(角丸パネルの内側を切りたい場合は外接矩形になる)。
    BeginFrameがスタックを空に戻すので、フレームをまたいでクリップが残ることはない。 PopClipRectし忘れたままEndFrameを迎えた場合は(最初の1回だけ)ログを出す。
  • GetLineHeight(fontSize, bold)は1行ぶんの高さ(ピクセル単位)を返す。 fontSizeからの推測ではなく、GDIのTEXTMETRICW::tmHeight+パディングから決まる 実際のセル高さに拡大率を掛けた値なので、フォントを差し替えても比率のずれが出ない。
    MeasureTextBlock(text, fontSize, outWidth, outHeight, bold)は改行を考慮した テキストブロック全体の幅(最も長い行の幅)と高さ(行高さ×行数)を返す。説明文を囲むパネルの 大きさを、描画前にAPI呼び出し1回で決められる。
  • かな漢字を含む任意のUnicode文字(BMP範囲)にも対応する。ASCII以外の文字は 初回のコンストラクタ実行時点ではアトラスに含まれていないため、DrawTextがアトラス未収録の 文字を検出すると、その文字だけをその場では描画せず、次のBeginFrame()の先頭でアトラスへ 追加してから以降のフレームで表示する(DX12のCreateTextureFromMemoryがコマンドリストを フラッシュ・リセットする都合上、通常の描画コマンドを積んだ後のフレーム中にアトラスを作り直すと レンダーターゲット/パイプラインステートの設定が失われクラッシュするため、追加は BeginFrame()の先頭でのみ行う設計になっている)。そのため新しい文字が最初に画面へ 現れる瞬間だけ1フレーム欠けることがあるが、通常のHUD表示(同じ文字列を毎フレーム描画し続ける用途) では気付かない程度の遅延で済む。

4. Library — 低レベルAPI上級者向け

KurenaiEngine3D/KurenaiEngine2D では対応できない独自の描画を組みたい 場合、Kurenai::RHI(DX11/DX12を抽象化したレンダリングAPI)・Kurenai::Core (ウィンドウ・カメラ)・Kurenai::Assets(モデル読み込み)を直接利用できます。 実際に KurenaiEngine3D/KurenaiEngine2D 自身もこのLibraryの上に 実装されています。

4.1 基本的な流れ

Core::Window window(L"My App", 1280, 720);
auto device = RHI::CreateDX11Device(); // または RHI::CreateDX12Device()
auto swapChain = device->CreateSwapChain(window.GetHandle(), window.GetWidth(), window.GetHeight());

// シェーダ・パイプラインステート・バッファ・テクスチャ・サンプラーを生成(通常は起動時に1回)
auto vs = device->CreateShader({ RHI::ShaderStage::Vertex, L"Shader.hlsl", "VSMain" });
auto ps = device->CreateShader({ RHI::ShaderStage::Pixel,  L"Shader.hlsl", "PSMain" });

RHI::PipelineStateDesc psoDesc;
psoDesc.InputLayout = { { "POSITION", 0, RHI::Format::R32G32B32_Float, 0 } };
psoDesc.VertexShader = vs.get();
psoDesc.PixelShader = ps.get();
psoDesc.RenderTargetFormats = { RHI::Format::R8G8B8A8_UNorm };
// SetRenderTarget(swapChain)はスワップチェーン付属の深度バッファも一緒にバインドするため、
// 深度テストを使わない場合でもこれをtrueにする(DX12で必要。下記の注記を参照)
psoDesc.DepthTargetAttached = true;
auto pipelineState = device->CreatePipelineState(psoDesc);

RHI::IRHICommandList* cmd = device->GetImmediateCommandList();
while (!window.ShouldClose())
{
    window.PumpMessages();

    cmd->SetRenderTarget(swapChain.get()); // スワップチェーン付属の深度バッファも同時にバインドされる
    cmd->ClearRenderTarget({ 0.05f, 0.05f, 0.08f, 1.0f });
    cmd->SetViewport({ 0, 0, (float)window.GetWidth(), (float)window.GetHeight(), 0.0f, 1.0f });
    cmd->SetPipelineState(pipelineState.get());
    // ... SetVertexBuffer / SetConstantBuffer / SetTexture / SetSampler / Draw ...

    swapChain->Present(true);
}

CreateTextureFromFile は拡張子(.dds/.tga/その他はWIC経由で png・jpg・bmp等)から自動判別する。sRGB=true はベースカラー等「見た目の色」を持つ テクスチャに、法線マップ等のデータ系テクスチャにはfalseを指定する。 CreateTextureFromMemory はRGBA8(1ピクセル4バイト、行間パディングなしのタイトパッキング)の ピクセルデータから直接テクスチャを作成する(実行時に生成したデータをアップロードする用途向け。 KurenaiEngine2D::DrawTextのフォントアトラス生成で使用)。

CreateDepthTextureArray はCreateDepthTextureのテクスチャ配列版で、 arraySize枚のスライスを1つのリソースとして作成する。書き込みは IRHICommandList::SetRenderTargetsのdepthArraySliceでスライスを選んで行い、 読み取りはシェーダ側でTexture2DArrayとして1本のスロットから行う。 カスケードシャドウマップのように「スライスごとに別の深度を描き、サンプル時はスライスを 動的に選びたい」用途で使う。

SamplerDesc(RHIDesc.h)はFilter(SamplerFilter::Linear / Anisotropic / Point)、AddressMode(SamplerAddressMode::Wrap / Clamp)、MaxAnisotropyを持つ。既定値はAnisotropic・Wrap・16xで、 浅い角度で見る面(床・路面など)のボケを抑える。AddressModeはAddressU/V/Wへまとめて適用される (軸ごとに別々の指定はできない)。用途ごとの選び方は次のとおり。

  • タイリングするマテリアルテクスチャ: Anisotropic + Wrap
  • 色バッファ・ルックアップテーブルのように「UVの端が定義域の端」であるもの: Linear + Clamp(Wrapだと端でフィルタのタップが反対側の端へ 回り込み、無関係な値が混ざる)
  • 深度・エンコードされた法線・metallic/roughness・シャドウマップのように、テクセルに格納された 値そのものに意味があり補間してはいけないもの: Point + Clamp

サンプラーは1個ずつではなくセット単位で扱う。CreateSamplerSetに SamplerDescの配列を渡すと、descs[i]がシェーダのregister(s(i))に 対応する1つの組ができ、描画パスの先頭でIRHICommandList::SetSamplerSetにより まとめてバインドする。countがバックエンドのスロット数に満たない場合、残りは 既定のサンプラーで埋められる。

CreateSamplerSetは描画を始める前(初期化時)にのみ呼ぶこと。 DX12実装はシェーダ可視ディスクリプタヒープへ直接書き込むため、描画中に呼ぶとGPUがまだ 読んでいる可能性のあるディスクリプタを壊す。セットの中身が作成後に不変であることが、 パスごとに異なるサンプラーを安全に使い分けられる根拠になっている (設計理由はIRHISamplerSet.hおよびArchitecture.html 14.2.2節)。

RHI::TextureImage::LoadFromFile(filePath, sRGB)(TextureImage.h)は ファイルのデコードのみを行い、GPUデバイスを必要としない静的関数。CreateTextureFromFileは 内部でこれを呼んでからCreateTextureFromImageでGPUリソース化しているだけであり、 両者を分離しているのは、デコード(CPU処理)をワーカースレッドで並列に行い、GPUリソース作成 (デバイスに紐づくため直列)だけを呼び出し元スレッドで行うため(4.6のAssets::LoadModelの 並列プリフェッチが実例)。

4.2.1 レイトレーシング

レイトレーシングはDX12かつDXR Tier 1.1対応のアダプタでのみ使える。 使う前に必ずSupportsRaytracing()で分岐すること。DX11は常にfalseを返す。 

if (device->SupportsRaytracing())
{
    // モデル1つ分のジオメトリからBLASを作る
    RHI::BottomLevelASDesc blasDesc;
    for (const auto& mesh : model.Meshes)
    {
        RHI::ASGeometryDesc geometry;
        geometry.VertexBuffer = mesh.VertexBuffer.get();
        geometry.VertexCount = mesh.VertexCount;
        geometry.VertexStrideInBytes = sizeof(Assets::Vertex);
        geometry.IndexBuffer = mesh.IndexBuffer.get();
        geometry.IndexCount = mesh.IndexCount;
        blasDesc.Geometries.push_back(geometry);
    }
    auto blas = device->CreateBottomLevelAS(blasDesc);

    // BLASへの参照とワールド変換からTLASを作る
    RHI::TopLevelASDesc tlasDesc;
    RHI::ASInstanceDesc instance;
    instance.BottomLevel = blas.get();
    instance.InstanceID = 0;   // シェーダがCommittedInstanceID()で受け取る値
    // instance.Transform は行優先3x4(平行移動はTransform[*][3])
    tlasDesc.Instances.push_back(instance);
    auto tlas = device->CreateTopLevelAS(tlasDesc);

    // コンピュートシェーダへバインドする(RaytracingAccelerationStructureとして読める)
    cmd->SetComputeAccelerationStructure(0, tlas.get());
}

CreateBottomLevelAS / CreateTopLevelAS は関数を抜けた時点でGPU上の構築が 完了している(内部で同期する)ため、戻り値をそのまま次の入力に使ってよい。 非対応環境や構築失敗時は例外を投げずログを出してnullptrを返す。 レイトレーシングは従来手法へフォールバックできる機能なので、失敗してもアプリを止めない設計にしてある。

シェーダへバインドできるのはTLASのみ(BLASを渡すとログを出して無視される)。 またdesc.Instancesが参照するBLASは、TLASより長く生存させること (理由はArchitecture.html 22.3節)。

頂点はモデルのローカル空間のままBLASへ登録し、ワールドへの配置は ASInstanceDesc::Transformで行う。Assets::ModelInstance::Worldは HLSLへそのまま渡せるよう転置済みで保持されているため、その先頭3行をコピーすれば Transformの行優先3x4と一致する。

レイを実際に飛ばすHLSLのRayQueryはシェーダーモデル6.5以上を要求する。 DX12バックエンドのシェーダーはdxc(DirectX Shader Compiler)でSM 6.5へコンパイルするため、 この要件は満たしている。DX11バックエンドは従来どおりd3dcompilerのSM 5.0のままで、 レイトレーシングにも対応しない(下記「シェーダーのコンパイル」参照)。

4.2.2 シェーダーのコンパイル

IRHIDevice::CreateShaderに渡すHLSLは、バックエンドによって異なるコンパイラで処理される。 書き方の違いを意識する必要はないが、使えるシェーダーモデルが変わる。

バックエンドコンパイラターゲット
DX12dxc(dxcompiler.dll)vs_6_5 / ps_6_5 / cs_6_5(デバイスの対応上限が6.5未満ならそこまで下げる)
DX11d3dcompilervs_5_0 / ps_5_0 / cs_5_0

DX12でdxcを使うにはdxcompiler.dllとdxil.dllが実行ファイルと同じフォルダに必要で、 ビルド時に自動でコピーされる(README.md参照)。dxcompiler.dllが見つからない場合は、 ログに警告を残したうえでDX12もd3dcompilerのSM 5.0へフォールバックする (その場合SupportsRaytracing()はfalseになる)。

HLSLの言語バージョンは-HV 2018で固定しているため、dxcのバージョンが上がっても 既存シェーダーの意味は変わらない。シェーダーファイルはBOM無しUTF-8で保存すること (日本語コメントを含む場合、BOMもUTF-16も使わない)。

固定しているのは意味を安定させるためであって、HLSL 2021で通らない書き方を許すためではない。 リポジトリ内のシェーダーは-HVを渡さない(= 既定のHLSL 2021)コンパイルも通る状態を保つこと。 特にベクタを条件にした三項演算子((v < 0.0f) ? a : bでvが float3等)はHLSL 2018では成分ごとのselectとして通るがHLSL 2021ではエラーになる。 select()は古いdxcに無いため、step()などどちらの言語バージョンでも 同じ意味になる書き方へ置き換えること。

4.2.2 bindless(ResourceDescriptorHeap)

bindlessはDX12かつシェーダーモデル6.6対応のアダプタでのみ使える。 使う前に必ずSupportsBindless()で分岐すること。DX11は常にfalseを返す。

RegisterBindlessはテクスチャ/バッファのSRVを恒久的なディスクリプタ区画へ登録し、 シェーダーがResourceDescriptorHeap[i]で引くための番号を返す。非対応環境・ 登録失敗時はRHI::kInvalidBindlessIndex(0xFFFFFFFF)を返す(例外は投げない)。 番号はIRHITexture::GetBindlessIndex() / IRHIBuffer::GetBindlessIndex()でも 取り出せ、リソースが破棄されるときに自動で返却される。 

const uint32_t index = device->RegisterBindless(texture.get());
if (index != RHI::kInvalidBindlessIndex)
{
    // この番号を定数バッファ等でシェーダーへ渡す。
    // HLSL側は Shaders/3D/Bindless.hlsli の BindlessSampleLevel などで引く
}

同じリソースを何度登録しても同じ番号が返るため、共有テクスチャで区画を無駄に消費することはない。 登録するのは「シェーダーから動的な番号で選びたいもの」だけにすること —— 区画の容量は有限で、固定スロット経由でしか読まないレンダーターゲット等まで登録すると食い潰す。

バッファを登録するにはSRVが要る。頂点バッファにStructuredBuffer<T>としての SRVも張るには、BufferDesc::ShaderReadable = trueを指定する (StrideInBytesがそのまま要素サイズになる)。同一リソースに頂点バッファビューと SRVを重ねて張るだけなので、メモリが二重に消費されることはない。

4.2.3 メッシュシェーダー

増幅シェーダー/メッシュシェーダーによる描画はDX12かつメッシュシェーダー Tier 1対応、 さらにbindlessが使えるアダプタでのみ使える(このエンジンのメッシュシェーダーは ジオメトリをbindlessで読む設計のため)。使う前に必ずSupportsMeshShader()で分岐すること。

ShaderStage::Amplification / ShaderStage::Meshで シェーダーを作り、MeshPipelineStateDesc(PipelineStateDescから 入力レイアウトと頂点シェーダーを除いたもの)でパイプラインステートを作る。 描画はSetVertexBuffer/SetIndexBuffer/DrawIndexedではなく IRHICommandList::DispatchMeshで行う。定数バッファ・テクスチャ・サンプラーの バインドは通常の描画とまったく同じAPI・同じ寿命で使える。 

if (device->SupportsMeshShader())
{
    RHI::MeshPipelineStateDesc desc;
    desc.AmplificationShader = amplificationShader.get(); // nullptrでもよい
    desc.MeshShader          = meshShader.get();
    desc.PixelShader         = pixelShader.get();
    desc.RenderTargetFormats = { RHI::Format::R8G8B8A8_UNorm };
    desc.HasDepthStencil     = true;
    auto pso = device->CreateMeshPipelineState(desc);

    cmd->SetPipelineState(pso.get());
    cmd->SetConstantBuffer(1, objectConstants.get());
    cmd->DispatchMesh(groupCount, 1, 1);
}

非対応環境ではCreateMeshPipelineStateがnullptrを、 CreateShaderもメッシュ系ステージではnullptrを返し、 DispatchMeshはログを残して何もしない。

SetShaderResourceBufferはBufferUsage::StructuredReadOnlyで作成した バッファをStructuredBuffer<T>としてピクセルシェーダへ読み取り専用でバインドする (要素数が可変で定数バッファに収めるには大きい配列向け。詳細は4.4参照)。スロット空間は SetTextureと共通(t0〜t11)のため、同じ描画内で テクスチャとスロットが衝突しないよう呼び出し側で調整すること。DX11バックエンドでは SetTextureと同様ピクセルシェーダからのみ参照できる。

バインドの寿命と呼び出し順

SetConstantBuffer / SetTexture / SetSamplerSet / SetShaderResourceBuffer のバインドは、同じスロットを上書きするまで維持される。 Draw/DrawIndexedをまたいでも、SetPipelineStateで パイプラインステートを切り替えても残るため、パス全体で共通のテクスチャはメッシュごとのループの外で 1回バインドすればよい。一度もバインドしていないスロットを読むと0が返る。 この挙動はDX11・DX12で完全に同一である。

例外として、SetTextureでバインドしたテクスチャを SetRenderTarget/SetRenderTargetsで描画先に指定すると、そのバインドは 自動的に解除される(同じリソースを読みながら書くことはできないため)。 コンピュートのSetComputeUnorderedAccessTexture/...Bufferも同じ理由で Dispatchのたびに解除されるので、ディスパッチごとにバインドし直すこと (SetComputeTextureのSRVは維持される)。

呼び出し順で1点だけ注意がある。同じバッファをUpdateBufferしてからバインドする場合は、 必ずUpdateBuffer → SetConstantBufferの順で呼ぶこと。 逆順にするとDX12で更新前の内容が参照される。

スロット番号の上限は定数バッファがb0〜b1、テクスチャ/構造化バッファが t0〜t11、コンピュートがb0〜b1・ t0〜t3・u0〜u3。範囲外を指定した場合は ログを出してバインドをスキップする。

4.3.1 コンピュートシェーダー

ShaderStage::ComputeでCreateShaderしたシェーダーを CreateComputePipelineStateに渡してコンピュート用パイプラインステートを作る。 グラフィックス用のSetPipelineState/SetConstantBuffer/SetTextureとは 別のレジスタ空間(DX12では専用のルートシグネチャ)を使うため、必ずSetCompute…系の 専用APIを使うこと。 

auto cs = device->CreateShader({ RHI::ShaderStage::Compute, L"Blur.hlsl", "CSMain" });
auto pso = device->CreateComputePipelineState({ cs.get() });
auto output = device->CreateUAVTexture(width, height, RHI::Format::R8G8B8A8_UNorm); // RWTexture2D

cmd->SetComputePipelineState(pso.get());
cmd->SetComputeTexture(0, inputTexture.get());              // t0 (SRV, 読み取り専用)
cmd->SetComputeUnorderedAccessTexture(0, output.get());     // u0 (RWTexture2D)
cmd->Dispatch((width + 7) / 8, (height + 7) / 8, 1);         // HLSL側は[numthreads(8, 8, 1)]

構造化バッファ(RWStructuredBuffer)を使う場合はBufferDesc::Usage = BufferUsage::Structured でCreateBufferし、SetComputeUnorderedAccessBufferでu0〜u3にバインドする。 Dispatchの直後に書き込み完了を保証するUAVバリアが自動的に発行されるため、続けて同じ リソースを別のDispatchやグラフィックスパスで読んでも呼び出し側でバリアを意識する必要はない。 DX11バックエンドも同じAPIで動作するが、UAVはDispatch呼び出しの範囲内でのみバインドされ、 呼び出し後に自動的にアンバインドされる(同一リソースをUAVとSRVへ同時バインドできないDX11の制約のため)。

4.3.2 Hi-Zミップチェーン

CreateHiZTexture(width, height, mipLevels)は、単チャンネル(R32_Float)で width/heightから1x1までのフルミップチェーンを持つテクスチャを作る。 通常のCreateUAVTextureが常に1ミップしか持たないのに対し、こちらは ミップごとに個別のUAVを張るため、SetComputeUnorderedAccessTextureの 第3引数mipLevelで「どのミップに書き込むか」を指定できる。SRV側は全ミップをまとめて見る 1枚のビューになっており(SampleLevelで任意のミップを読む用途、ミップ0のコピー元は別テクスチャ)、 ミップ単位で読みたい場合はUAVを読み取り専用として使う(下記例のように隣接ミップを2枚ともUAVでバインドする)。 

auto copyCs = device->CreateShader({ RHI::ShaderStage::Compute, L"HiZ.hlsl", "CSCopy" });
auto copyPso = device->CreateComputePipelineState({ copyCs.get() });
auto downsampleCs = device->CreateShader({ RHI::ShaderStage::Compute, L"HiZ.hlsl", "CSDownsample" });
auto downsamplePso = device->CreateComputePipelineState({ downsampleCs.get() });

const uint32_t mipLevels = /* floor(log2(max(width, height))) + 1 */;
auto hiZTexture = device->CreateHiZTexture(width, height, mipLevels);

// ミップ0: 通常の深度テクスチャ(1ミップ)からコピーする
cmd->SetComputePipelineState(copyPso.get());
cmd->SetComputeTexture(0, depthTexture.get());                    // t0 (SRV)
cmd->SetComputeUnorderedAccessTexture(0, hiZTexture.get(), 0);    // u0 = ミップ0
cmd->Dispatch((width + 7) / 8, (height + 7) / 8, 1);

// ミップ1以降: 1つ前のミップを読み、2x2ブロックの最小値(Reverse-Zのため最も遠い深度)を次のミップへ書く
cmd->SetComputePipelineState(downsamplePso.get());
for (uint32_t mip = 1; mip < mipLevels; ++mip)
{
    cmd->SetComputeUnorderedAccessTexture(0, hiZTexture.get(), mip - 1); // u0 = 読み取り元ミップ
    cmd->SetComputeUnorderedAccessTexture(1, hiZTexture.get(), mip);     // u1 = 書き込み先ミップ
    cmd->Dispatch(/* 出力ミップの幅高さに応じたグループ数 */);
}

最小値でダウンサンプルするのは、このエンジンがReverse-Z(近平面=1.0/遠平面=0.0、深度比較はGREATER)を 使っているため。あるブロックの最小深度値は 「そのブロック内で最も遠い可視サーフェス」を表し、候補オブジェクトの最も近い点でさえこの値より 奥であれば、ブロック内のどのピクセルにも遮蔽されていることが保証できる(非Reverse-Zで最大値を 取る一般的なHi-Zカリング手法を、Reverse-Zの向きに合わせて反転させたもの)。KurenaiEngine3D はG-Buffer深度からこのミップチェーンを毎フレーム構築しているが、現時点ではオクルージョンカリングや SSRのレイマーチング高速化といった利用箇所は未実装で、デバッグ表示(Render Targets - Hi-Z)でのみ 内容を確認できる。

バインドスロットの上限(DX12バックエンドが固定のルートシグネチャで実装されているため、 DX11/DX12共通でこの範囲を守る必要がある):

定数バッファ更新の制約: CreateBuffer にInitialDataを 渡すかどうかで、後からUpdateBufferできるかがDX11/DX12で挙動が変わる。

  • 毎フレーム更新する定数バッファ(BufferUsage::Constant): InitialData = nullptr で作成し、以後UpdateBuffer()で毎フレーム書き込む(DX11ではInitialDataを渡すと IMMUTABLEになり以後の更新が失敗するため、必ずnullptrで作成すること)。
  • 頂点/インデックスバッファ(BufferUsage::Vertex/Index): InitialDataを渡して作成する静的ジオメトリ専用。生成後にUpdateBufferしては いけない(DX12ではGPU読み取り専用のDEFAULTヒープに配置されるため未定義動作になる)。移動・回転・ 拡縮は定数バッファ経由のワールド行列で表現する。

4.4 その他のRHI型

IRHIBuffer / IRHITexture / IRHIShader / IRHIPipelineState / IRHISamplerSet / IRHISwapChain はいずれも 中身を持たない不透明なハンドル型。std::unique_ptr<IRHIXxx>として保持し、 IRHICommandListの各メソッドに生ポインタ(.get())で渡す。 RHIDesc.h(BufferDesc, ShaderDesc, InputElementDesc, PipelineStateDesc, ComputePipelineStateDesc)とRHIEnums.h (ShaderStage: Vertex/Pixel/Compute、 BufferUsage: Vertex/Index/Constant/Structured(コンピュートシェーダー用のRWStructuredBuffer)/ StructuredReadOnly(CPUから毎フレームUpdateBufferで書き換え、 シェーダからはStructuredBuffer<T>として読み取り専用。SetShaderResourceBufferで グラフィックスパイプラインへバインドする。要素数が可変で定数バッファに収めるには大きい配列 — KurenaiEngine3Dのポイント/スポットライトリストが実例 — 向け)、 Format, BlendMode など)に描画リソースの 記述構造体・列挙型がまとまっている。PipelineStateDesc::BlendModeには Opaque(既定・不透明)、AlphaBlend(標準アルファブレンド)、 Additive(加算合成。炎・光などの発光エフェクト向け)、 Multiply(乗算合成。影・すりガラスなどの減光表現向け)、 PremultipliedAlpha(事前乗算済みアルファブレンド)を指定できる。 IRHIGPUProfiler(GPUタイムスタンプ計測)、 IRHIImGuiBackend(ImGui連携)も同様に公開されている。

深度に関わるPipelineStateDescのフラグは2つある。HasDepthStencilは 深度テストを行うかで、DepthTargetAttachedは 深度テストはしないが描画時に深度バッファがバインドされた状態になるかを表す。 後者はDX12が「パイプラインステートが想定する深度フォーマット」と「実際にバインドされている深度バッファ」の 一致を要求するために必要で、SetRenderTarget(swapChain)はスワップチェーン付属の深度バッファを 必ずバインドするため、スワップチェーンへ直接描くパイプラインステートでは深度テストを使わなくても DepthTargetAttached = trueにする(HasDepthStencil = trueで代用すると 意図しない深度テストが有効になってしまう)。SetRenderTargetsで深度テクスチャに nullptrを渡すパスでは両方ともfalseのままでよい。

4.6.1 ライトの読み込み(Model::Lights)

モデルファイルにポイント/スポット/平行光が含まれる場合、Model::Lights (std::vector<Assets::Light>)として読み込まれる。glTFは KHR_lights_punctual 拡張、FBXはLightノードから読み込む(抽出自体はKurenaiPacker.exeが パック時に行い、.kmodelのLightEntry[]として格納する。ランタイムはそれを そのまま読むだけで、assimpには依存しない)。 

enum class LightType { Directional, Point, Spot };

struct Light
{
    LightType Type;
    float Position[3];         // ローカル座標(モデル自身の空間。Directionalでは未使用)
    float Direction[3];        // 光が進む向き(正規化済み)。Spot/Directionalで使用
    float Color[3];            // 線形色。最大成分が1になるよう正規化済み
    float Intensity;           // 測光量。Point/Spotはカンデラ(cd)、Directionalはルクス(lx)
    float Range;                // 影響半径。Directionalでは未使用
    float SpotInnerConeAngle;   // ラジアン。Spotのみ
    float SpotOuterConeAngle;
    bool Enabled;
    std::string Name;
};
  • Intensityの単位は物理量。glTFはKHR_lights_punctualの値 (カンデラ/ルクス)をそのまま読み込むため正確。FBXには物理単位が存在しないため、DCC側の Intensityプロパティをカンデラ相当として近似する(精度は保証されない)。
  • 表示上の明るさは測光量に実在の写真露出値EV100(KurenaiEngine3Dの Lightingパネルの「EV100」)を直接掛けて求める(exposure = 1 / (1.2 * 2^EV100))。 太陽光・環境光にも同じ露出が一様にかかる、シーン全体で単一の設定になっている。EV100は値が 大きいほど明るいシーンを表す実在の写真用語であり、値を上げるほど描画は暗くなる (Photoshop等の「露出」スライダーとは向きが逆なので注意)。
  • RangeはglTFにノードのメタデータPBR_LightRangeがあればその値を 使う。無ければ打ち切り輝度からEV100=15.0(既定値)を仮定して逆算した推定値が入る (この推定はKurenaiPacker.exeのパック時に一度だけ行われるため、後からEV100を大きく変更すると 実際に見えるべき範囲と合わなくなることがある。その場合はImGuiでRangeを手動調整する)。
  • 平行光は太陽光との二重照明を避けるため、読み込み時は既定でEnabled = false になる(ImGuiから有効化できる)。
  • エリアライト(球・チューブ・矩形)は未対応。glTFの KHR_lights_punctualにエリアライトの定義が無く、FBXのエリアライトはassimpが 未対応種別として扱うため、いずれの形式からも読み込めない。
  • Position/Directionは.kmodel内ではモデル自身の ローカル空間のまま保持される。複数モデルをシーン上へ配置する場合(下記4.7)、 Assets::LoadSceneが各ModelInstance::Worldでワールド空間へ変換し、 .kscene自身の[Light]セクションのライトと合成した Scene::Lightsとして返す。

4.6.2 パッケージ読み込みと並列プリフェッチ

.kmodelが参照するユニークな.ktexは、ModelLoader.cpp内の TextureLoader::LoadAllがワーカースレッドで並列にデコードする。パック済みの .ktexは既にBC7圧縮・ミップ生成済みのDDSペイロードを持つため、ランタイム側では RHI::TextureImage::LoadFromPackedTextureによるファイル読み込み+DDSデコードのみが 発生し、WICデコード・ミップ生成・GPU BC7圧縮は一切走らない(これらは全てKurenaiPacker.exeが パック時に済ませている)。デコード自体はGPUデバイスを必要としないためワーカースレッドで 並列化できるが、GPUリソース化(device.CreateTextureFromImage)はデバイスに紐づく 処理のため呼び出し元スレッドで直列に行う。テクスチャ個別の読み込みに失敗した場合は、 スロットの種類に応じて白/フラット法線/マゼンタのプレースホルダーへフォールバックし、 モデル全体の読み込みは継続する。

各メッシュのノード変換(ワールド行列)はパック時に頂点座標へ焼き込み済みのため、 Model自体を描画する分には別途ワールド行列を掛ける必要はない (複数モデルをシーン上の別位置へ配置する場合は下記4.7のAssets::LoadSceneを使う)。 頂点レイアウトはPOSITION(R32G32B32_Float, offset=0), NORMAL(R32G32B32_Float, offset=12), TEXCOORD0(R32G32_Float, offset=24), TANGENT(R32G32B32A32_Float, offset=32)(Assets::Vertex, 48バイト)。 インデックスは常に32bit固定。

.kmodelのバージョンがランタイムと一致しない、ファイルが壊れている、参照する .kgeom/.ktexが見つからない等、読み込みに失敗した場合は std::runtime_errorを投げる(呼び出し前と異なりフォールバック先が無いため)。 個々のテクスチャの読み込みに失敗した場合はモデル全体は読み込みを継続し、白1x1 (BaseColor/MetallicRoughness)またはフラット法線(Normal)、あるいは目立つマゼンタ色の プレースホルダーに差し替えられる。

4.6.1 パッケージ読み込みと並列プリフェッチ

.ktexはKurenaiPacker.exeがWICデコード・ミップ生成・GPU BC7圧縮を事前に済ませた DDSペイロードをそのまま格納したファイルのため、LoadModelはファイルを読んで DirectX::LoadFromDDSMemoryでデコードするだけでよく、WICデコード・ミップ生成・ BC7圧縮のいずれも実行時には発生しない。

それでも大量のテクスチャを持つモデル(Bistro等)では、ファイルI/Oとデコードの合計時間を 短縮するためLoadModelはモデル1つぶんのテクスチャ読み込みをまとめて並列化する (ModelLoader.cpp内のTextureLoader::LoadAll、論理コア数を上限8で クランプしたワーカースレッドを使う)。各ワーカーが行うのは RHI::TextureImage::LoadFromPackedTextureによるファイル読み込み+DDSデコードのみで GPUデバイスを必要としないため安全に並列化できる一方、GPUリソース作成 (device.CreateTextureFromImage)自体はデバイスに紐づく処理のため呼び出し元スレッドで 直列に行う。

4.6.3 アルファモード(カットアウト/半透明)

MeshはglTFのalphaModeに応じてAlphaCutoffと IsTransparentのいずれかが設定される(両方が同時に立つことはない)。

  • alphaMode = "MASK" — AlphaCutoff(既定0.5)が設定され、ベースカラー テクスチャのアルファがこの値未満のピクセルは描画されない(葉・網戸などのカットアウト表現)。 不透明物体と同じジオメトリパスで描画される。
  • alphaMode = "BLEND" — IsTransparent = trueになり、 KurenaiEngine3Dではジオメトリパス(G-Buffer)には描画されず、専用の半透明フォワードパスで 奥から手前の順にアルファブレンド合成される(不透明物体には隠れるが、AO/間接光・SSR等の ポストプロセスは適用されない。既知の制約の詳細は実装者向け ドキュメント14章参照)。色・不透明度はbaseColorTexture.rgba * baseColorFactor (glTF仕様どおり)で決まる。テクスチャを持たずbaseColorFactorのみで色/不透明度を指定するマテリアル (ガラス等でよくあるパターン)も正しく反映されるが、baseColorFactor.a自体が 1.0(不透明)のマテリアルはalphaMode=BLENDが付いていても見た目上は 不透明のまま描画される(モデルデータがそう定義しているため。実例・詳細は 実装者向けドキュメント14.7/14.8節参照)。
  • alphaMode = "OPAQUE"(既定)または非対応形式(FBX/OBJ等) — 常に不透明として扱われる。

4.7 シーンファイル(.kscene)と Assets::LoadScene

Scene LoadScene(RHI::IRHIDevice& device, const std::wstring& sceneFilePath, const std::wstring& assetRootDirectory);
std::wstring ReadSceneName(const std::wstring& sceneFilePath);

.ksceneは複数モデルの配置(平行移動・回転・スケール)とカメラ・太陽光の初期値を 1ファイルにまとめる、UTF-8のテキスト形式。バイナリ変換を経ずランタイムが直接パースするため、 配置や太陽の向きをKurenaiPackerの再実行なしに即座に調整できる。Assets::KurenaiEngine3Dは 起動時に<DLLフォルダ>/Assets/Scenes/*.ksceneを列挙し、ImGuiの「シーン」パネルへ ファイル名の昇順で並べる(表示名はReadSceneNameが読む[Scene] Name、 省略時はファイル名)。

LoadSceneは[Model]ごとにAssets::LoadModelを実際に呼び出し、 TRS(平行移動・回転・スケール)から計算したワールド行列・法線行列(逆転置)・ TangentSignFlip(負スケール時の従法線反転補正)を持つModelInstanceの 配列としてSceneを返す。各モデルのAABBをワールド変換して合成したシーン全体のAABBも 保持し、カメラの自動配置やシャドウマップのフィッティングに使われる。失敗時は std::runtime_errorを投げる(ファイル名・行番号・該当行の内容をログに出力する)。

[ReflectionProbe]は反射プローブを配置します。指定した位置から周囲を キューブマップへキャプチャし、影響範囲の内側のピクセルはその環境をIBLの環境ソースとして使います。 屋内など、シーン全体で共通のスカイボックス由来の環境光では空が映り込んでしまう場所で、 実際の壁・柱・床が映るようになります。影響範囲の外側は従来どおりスカイボックス由来のIBLになります。 不透明な物体だけでなく半透明な物体(ガラスなど)にも同じように効きます。 半透明にはSSRが効かないため、プローブの有無が最も分かりやすく現れるのはむしろガラスです。

影響範囲はShapeで球(Sphere、Radiusで指定)と 直方体(Box、BoxExtentsとYawで指定)から選べます。 Boxには、影響範囲を部屋の形に沿わせられることに加えて視差補正が 効くという利点があります。プローブのキューブマップは1点から撮ったものなので、プローブ位置から 離れた壁際では映る像の位置が本来の反射位置とずれます。視差補正は反射ベクトルをこの箱と交差させ、 その交点の方向でキューブマップを引き直すことでずれを打ち消します。そのため BoxExtentsは部屋の壁とおおよそ一致させてください(実際の壁から大きく離すと 補正がかえってずれます)。

ImGuiの「Reflection Probes」パネルにある「Use Depth Cube」を入れると、 箱ではなくキャプチャ時に一緒に焼いた実際の距離を辿って反射を当てます。部屋が 直方体から外れている場合や、球のように強く曲がった鏡面で反射像が二重に割れる場合に効きます (このとき箱は「探索範囲の上限」としてのみ使われるため、BoxExtentsを部屋に合わせる 重要度は下がります)。ただし引き換えに、焼いた距離の解像度に由来する階段状のエッジが 反射像に乗るため、既定では無効にしてあります。

同じパネルの「Occlusion (Reduce Light Leak)」も同じ距離を使い、プローブから見えない 位置(壁の向こう)のピクセルでそのプローブの寄与を落とします。ただしプローブが少ないうちは、 落ちた分をより明るい空由来のIBLが埋めるため物体の真下が逆に明るくなることがあり、 既定では無効にしてあります。

影響範囲が重なっているプローブ同士は、BlendDistance(境界から内側へ重みが1まで 立ち上がる距離)に応じた重み付き平均で混ざります。どのプローブの重みも1に満たない場所では 残りをスカイボックス由来のグローバルIBLが埋めるため、影響範囲の外へ出るときも境界で切り替わらず 徐々に元の環境光へ戻ります。

プローブの中身はシーンのジオメトリ・ライトに依存するため、シーン読み込み時に自動で焼かれます。 実行中にライトや時刻を変えた後に反映したい場合は、ImGuiの「Reflection Probes」パネルの 「Bake」ボタンを押してください(同パネルでプローブの追加・削除・位置と影響範囲の編集もできます。 影響範囲だけを変えた場合は焼き直し不要です)。

同パネルの「Update Mode」で焼き直しの方式を選べます。 Bakedはシーン読み込み時と「Bake」ボタンのときだけ焼きます(実行時コストはゼロですが、 ライトや時刻を動かしても反射は焼いた時点のまま止まります)。 On Demandは加えて、太陽・時刻・ライトなど焼き上がりに影響する状態の変化を検出して 自動で焼き直します(変化していない間のコストはゼロですが、変化したフレームに全プローブぶんの 焼き直しが集中します)。 Realtimeは1つのプローブを12フレームかけて更新します(前半6フレームで1面ずつ撮り、 後半6フレームで1面ぶんずつぼかしてから次のプローブへ回ります)。 1回のフレームに処理が集中してカクつくのを防ぐためで、実測でもこのぼかしの処理は 1フレームあたり1〜3ミリ秒に収まっています(分割していなかった頃は6フレームに1回だけ 20ミリ秒前後の山が出ていました)。 なお時刻を大きく動かして場面全体の明るさが2倍以上変わったときだけは、Bakedでも 自動で焼き直します。プローブには焼いた時点の明るさの数値が入っているため、これを持ち越すと 反射だけが桁違いの明るさになってしまうためです。 各方式のコストはImGuiの「Profiler」パネルでProbeBake0/ProbeBake1、 ProbeRealtimeCapture、ProbeRealtimeConvolveとして比較できます。同パネルの「Parallax Correction」「Probe Blending」で 視差補正・ブレンドの有無を切り替えて見比べることもできます。上限は8個で、超えた分は警告ログを 出してスキップします。現時点では箱の回転はY軸まわりのみで、影響範囲の箱がそのまま視差補正の 投影ボックスを兼ねます(両者を別々に指定することはできません)。内部実装は 実装者向けドキュメント 19章「反射プローブ」を参照してください。

[GIVolume]はDDGI(拡散グローバルイルミネーション)のプローブ格子を置きます。 反射プローブが鏡面の映り込みを担うのに対し、こちらは拡散の間接光を担当し、 「壁の色が床へ回り込む」ようなカラーブリーディングを出します。これが無いと、密閉された室内の壁にも 遮られていない空の環境光がそのまま乗ります。有効な間はDDGIが拡散の環境ソースを 差し替えます(グローバルIBLへ加算するのではありません)。反射プローブは鏡面専任なので 拡散のイラディアンスを持たず、DDGIボリュームの外に出た場合はグローバルIBLへ戻ります。 鏡面には一切影響しません。

プローブは格子状に自動配置されるため、位置を1個ずつ指定する必要はありません。壁の内側に プローブが1個も入らないとそこだけ間接光が外挿になるので、Originは壁から少し内側へ 置いてください。NormalBiasを0に近づけると画面全体が一様に暗くなります (面が、自分を照らしているプローブから見えていないと誤判定するためで、強度で持ち上げるのではなく このバイアスで直します)。

明るさは時間をかけて収束します。バウンスが1フレームに1回ずつ積み上がり、さらに 1フレームあたり一定数のプローブしか焼き直さないためで、455プローブの既定設定ではおよそ数十秒かかります。 ImGuiの「レンダリング」パネルの「DDGI (拡散グローバルイルミネーション)」でON/OFF・強度・ 1フレームに更新するプローブ数を変えられます。「デバッグ表示」ではイラディアンスと距離モーメントの アトラスを直接確認できます。ボリュームは現状1個だけ使われ、2つ目以降は警告を出して 無視します。内部実装は 実装者向けドキュメント 31章「DDGI」を参照してください。

[Light]で指定したライトはワールド空間の値として扱われ、モデル埋め込みのライト (4.6.1節参照)と合成されたScene::Lightsとしてそのまま描画に反映される (カンデラ/ルクス・EV100露出の扱いは4.6.1節と同じ。内部実装は 実装者向けドキュメント 11章「複数ライト」を参照)。

パースの規則: ファイルはUTF-8(BOM許容)。#は行頭、または直前が 半角空白/タブの場合のみコメント開始とみなす(Path = Textures/#1/foo.kmodelのように 非空白文字に直接続く#は文字通り扱われ、パスが壊れない)。key = valueは 最初の=だけで分割する。値の前後の半角空白/タブのみをトリムし、値全体が"で 囲まれている場合は引用符を剥がして中身を一切トリムしない(前後に意図的な空白を含むパスや、 非空白直後でない#から始まるパスを書きたい場合に使う)。未知のセクション・未知のキーは 警告ログを出してスキップする(前方互換性のため、将来項目が増えても古いランタイムが落ちない)。

5. 入力について

KurenaiEngineBase はGetAsyncKeyState/GetCursorPosのような グローバル(システム全体)の入力状態ではなく、ウィンドウスコープのメッセージベース入力API を提供します。内部でWM_MOUSEMOVE/WM_LBUTTONDOWN/WM_KEYDOWN等の ウィンドウメッセージから状態を更新するため、ウィンドウがフォーカスを失っている間は反応せず、 PostMessageによるテスト自動化(実デスクトップのカーソル・フォーカスに影響を与えない)とも 整合します。 

bool IsMouseOverWindow() const;                    // カーソルがクライアント領域内にあるか
bool IsMouseButtonDown(MouseButton button) const;   // 現在押されている状態か(継続的な操作に使う)
bool WasMouseButtonPressed(MouseButton button) const; // 直前のPumpEvents()中に押された(エッジ検出)か
bool WasMouseButtonReleased(MouseButton button) const; // 直前のPumpEvents()中に離された(エッジ検出)か
bool IsKeyDown(KeyCode key) const;                     // 同上(キー)。WASD移動など「押している間」続く操作に使う
bool WasKeyPressed(KeyCode key) const;                 // 同上(キー)。オートリピートは無視する
bool WasKeyReleased(KeyCode key) const;                // 同上(キー)の解放エッジ
POINT GetClientMousePosition() const;               // クライアント座標(原点は左上、Y-down)
float GetMouseWheelDelta() const;                   // 直前のPumpEvents()中のホイール回転量(ノッチ単位、奥が正)
  • MouseButton は Left/Right/Middle の3値。
  • KeyCode はWin32仮想キーコード(VK_ESCAPE、'A'〜'Z'など) をそのまま使う int のエイリアス。GetAsyncKeyStateで使っていたキー定数を そのまま流用できる。
  • Is*Down系は「現在押されている状態」を返すレベル状態。WASD移動のような 「押している間」継続する操作に使う。Was*Pressed系は「離れた状態から押された状態になった」 エッジのみを検出する。判定対象の期間は直前のPumpEvents()呼び出し中 (1フレームにつき1回呼ぶ想定)。
  • Was*Released系はWas*Pressed系と対になる解放エッジ。一般的なUIのボタンは 押下ではなく「押下→同じボタン上での解放」でクリックを確定する(押したまま領域外へ カーソルを出せばキャンセルできる)ため、UI基盤を組む場合はこちらを使う。 Is*Downの前フレーム値を呼び出し側で保持する方法とは違い、1回の PumpEvents()の中で押して離した場合も取りこぼさない。
    ウィンドウがフォーカスを失った場合、その時点で押されていたキー・ボタンは 「解放された」として通知される。押下だけ受け取って解放が来ないと、UIが押しっぱなしの状態で 固まってしまうため。
  • GetClientMousePositionが返す座標はWin32標準のクライアント座標(原点は左上、Y-down)。 KurenaiEngine2D::DrawSpriteのワールド座標(原点は左下、Y-up。3.1節参照)とは上下が逆なので、 スプライト座標と突き合わせる場合はKurenaiEngine2D::ClientToWorld (またはGetMouseWorldPosition)で変換すること(3.2節)。 カメラ位置・ズーム・論理解像度によるレターボックスをすべて考慮するため、 height - yのような自前の変換と違ってカメラを動かしてもずれない。
  • これらはいずれもKurenaiEngineBaseのメンバなのでKurenaiEngine2D/ KurenaiEngine3Dどちらからも呼べる。KurenaiEngine3D::Run()自身も 移動(WASD/E/Q)・速度切り替え(Shift)・ImGui表示切り替え(F1)にこのAPI(IsKeyDown/ WasKeyPressed)を使っており、PostMessageによるキー操作のテスト自動化と 整合する。ただし右クリックドラッグによる視点回転(マウスルック)だけは意図的に例外で、 実カーソルの位置取得・固定(GetCursorPos/SetCursorPos)による無限ドラッグを 実現するためGetAsyncKeyState(VK_RBUTTON)のままにしている。これにより PostMessageでWM_RBUTTONDOWNを送っても実カーソルの位置・表示状態には 一切影響しない(意図しないカーソル操作の経路にならないことを構造的に保証している)。
  • 複数キー・複数ボタンの同時押しにも対応(それぞれ独立して状態を保持)。
  • GetMouseWheelDeltaはWM_MOUSEWHEELの回転量を WHEEL_DELTA(120)で割ったノッチ数を返す。奥へ回すと正で、 回転していなければ0。エッジ系と同じく寿命は直前のPumpEvents()呼び出しぶんで、 その間に複数のメッセージが届いた場合は合算される。高分解能ホイールは1ノッチ未満を 刻んで送ってくるため戻り値はfloat。
    なおWM_MOUSEWHEELの座標は他のマウスメッセージと違いスクリーン座標で 届くため、GetClientMousePositionの更新には使っていない。 ホイール操作の位置が要る場合はGetClientMousePositionの値 (直近のWM_MOUSEMOVEの位置)を使うこと。
  • IsMouseOverWindowは、環境変数KURENAI_INPUT_AUTOMATION=1が設定されている 場合に限り、下記のImGui側と同様の理由でTrackMouseEvent由来のWM_MOUSELEAVE ノイズを抑制する。実カーソルがウィンドウ外にある状態でPostMessageにより WM_MOUSEMOVEを注入すると、直後に実カーソル位置に基づくWM_MOUSELEAVEが 割り込み、素朴に実装するとIsMouseOverWindowが真になった直後に偽へ戻ることを 繰り返してしまう。これを防ぐため、直近100ms以内にWM_MOUSEMOVEを処理していれば、 その後届いたWM_MOUSELEAVEは古い実カーソル位置によるノイズとみなして無視する (実際にウィンドウ外に出た場合も、新たなWM_MOUSEMOVEが来ない限りこの猶予はすぐ 過ぎるため、通常どおり検出される)。この環境変数は自動操作テストのハーネスが対象exeの起動前に 設定する想定のもので、未設定の通常起動ではこの抑制ロジック自体が完全に無効となり、 実際のマウス操作には一切影響しない。
  • ImGuiパネルの操作(ボタンクリック等)をPostMessageで行う場合、 WM_MOUSEMOVE → WM_LBUTTONDOWN → WM_LBUTTONUPの3つを 間隔を空けずに連続送信すること。Dear ImGuiのWin32バックエンド (imgui_impl_win32.cpp)は、ウィンドウがフォーカスされている間かつ 直近に有効なマウス位置追跡が無い場合、実カーソル位置(GetCursorPos)を毎フレーム ポーリングしてio.MousePosに上書きするフォールバック動作を持つ。さらに TrackMouseEventによるWM_MOUSELEAVE検出も実カーソル位置基準のため、 実カーソルがウィンドウ外にある状態でWM_MOUSEMOVEを送ると、ほぼ即座に(実カーソルの 位置に基づく)WM_MOUSELEAVEが発生し、次のフレームで実カーソル位置へ上書きされてしまう。 3メッセージを間隔を空けずに送ることで、この上書きが発生する前に同一フレーム(またはごく近い フレーム)内でクリック判定を完了させられる。

5.1 ImGuiがマウス・キーボードを掴んでいる間の入力抑止

KurenaiEngine3D::Run()は、ImGuiのパネルが入力を掴んでいる間はカメラ操作を止めます。 ライトの名前をテキスト入力欄で編集している最中に、WやDがカメラ移動として解釈されてしまうのを 防ぐためです。判定にはImGuiが提供するio.WantCaptureKeyboard/ io.WantCaptureMouseを使います。

  • キーボード: WantCaptureKeyboardが真の間はWASD/E/Qによる移動を 処理しない。F1(ImGuiパネルの表示/非表示)だけは意図的に抑止しない。ここも 止めてしまうと、入力中にパネルを畳んで元へ戻す手段が無くなり、入力欄からフォーカスを外す方法 (Esc / 別の場所をクリック)を知らないと操作不能になるため。ImGuiのInputTextは F1を消費しないので、通しても入力内容には影響しない。
  • マウス: WantCaptureMouseが真のときは視点回転を開始しない (パネル上での右クリックメニュー操作と衝突するため)。一度回転を始めた後はカーソルが画面中央へ 固定され続けてImGui側の判定が変わりうるので、この判定は開始時にだけ行う。
  • ImGuiの状態を読めるのは描画スレッドだけで、移動・視点回転を処理するのは呼び出し元スレッド (Run()を呼んだスレッド)のため、この2つの真偽値はstd::atomic<bool>で 描画スレッドから受け渡される。描画は1フレーム遅れて行われるためこの値も1フレーム遅れるが、 WantCaptureKeyboardは入力欄がアクティブな間ずっと真であり続けるので、実用上ずれるのは 押し始めの1フレームだけになる。
  • この抑止はImGuiパネルが表示されているときだけ働く。F1で非表示にしている間は どちらの値も偽として扱われ、カメラ操作は常に効く。

PostMessageによる自動化でカメラ操作を確かめる場合、テキスト入力欄にフォーカスが 残っていると意図した移動が起きない点に注意してください。

6. サウンド再生について

KurenaiEngineBase はXAudio2による簡易なサウンド再生APIを提供します。WAV(PCM)ファイルの 読み込み・再生・停止・音量制御に対応した最小限の実装です(効果音・BGM程度の単純な再生が目的で、 ピッチ・パン・カテゴリ別のバス等は持ちません)。 

SoundHandle LoadSound(const std::wstring& filePath);
VoiceHandle PlaySound(SoundHandle sound, float volume = 1.0f, bool loop = false);
void StopSound(VoiceHandle voice);
void SetVoiceVolume(VoiceHandle voice, float volume);  // 再生中ボイスの音量(0.0〜1.0)
void SetMasterVolume(float volume);                    // 全ボイスに掛かる音量(0.0〜1.0)
float GetMasterVolume() const;
  • LoadSound はWAV(PCM)ファイルを読み込み、SoundHandleを返す (TextureHandleと同様、ロード時にまとめて呼び、返ってきたハンドルを保持しておいて PlaySoundに渡す)。
  • PlaySound は呼び出しのたびに新しいボイスを生成するため、同じサウンドを重ねて (前の再生が終わる前に再度)鳴らすことができる。volumeは0.0〜1.0。戻り値の VoiceHandleはStopSoundに渡す再生中ボイスの識別子。
  • loop=trueの場合、そのボイスはStopSoundで明示的に止めるか KurenaiEngine2D/KurenaiEngine3Dが破棄されるまで無限ループし続ける。 単発再生(loop=false)は自動的に終了するため、通常StopSoundを呼ぶ必要はない (呼んでも問題はない)。
  • SetVoiceVolume は再生中のボイスの音量を変更する。 フェードイン/フェードアウトはこれを毎フレーム呼ぶ形でアプリ側が実装する (ループBGMを短い間隔でStopSound→PlaySoundし直す方法は、 再生位置が先頭へ戻るため代用にならない)。既に終了済み/無効なハンドルの場合は何もしない ――単発再生がいつ終わるかは呼び出し側には分からないため、これは正常系でログも出ない。
  • SetMasterVolume は全ボイスに掛かる音量で、個々のボイスの音量とは掛け算になる。 BGM/SEといったカテゴリ別のバスは持たないため、 設定画面でカテゴリごとに調整したい場合はカテゴリごとにVoiceHandleを覚えておき SetVoiceVolumeで調整する。
  • 音量はいずれも0.0〜1.0。範囲外(NaNを含む)を渡すとログを出して範囲内へ丸める (音量の指定ミスでアプリを落とす価値は無いため例外にはしない)。
  • これらはKurenaiEngineBaseのメンバなのでKurenaiEngine2D/ KurenaiEngine3Dどちらからも呼べる。
  • 使用にはCOM初期化(CoInitializeEx)が必要(WICテクスチャ読み込みと同じ要件。 8章参照)。

7. ビルドに必要な追加の依存ファイル

KurenaiEngine3D/KurenaiEngine2D/Library のいずれを 使う場合でも、サンプルプロジェクト自身がDirectXTexのヘッダー・ライブラリを直接参照する 必要はありません(KurenaiEngineLibrary.dll内部にリンク済み)。assimpは KurenaiEngineのいずれのDLLにもリンクされていない(モデル解析はすべてオフラインの KurenaiPacker.exe側で行うため)。サンプルプロジェクトに必要なのは以下だけです。

  • インクルードディレクトリ: KurenaiEngine\Source\Engine (Libraryも使う場合は KurenaiEngine\Source\Library も追加)
  • KurenaiEngineLibrary.vcxproj と、使う方(KurenaiEngine3D.vcxproj または KurenaiEngine2D.vcxproj)への2つのプロジェクト参照(自動的に両方の インポートライブラリがリンクされる。DLLを経由した参照は推移的にリンクされないため、 Libraryへの参照だけを省略することはできない)
  • 実行時に上記2つのDLLが実行ファイルと同じフォルダに存在すること
  • DX12バックエンドを使う場合は、加えてWindows SDK同梱のdxcompiler.dllと dxil.dllが実行ファイルと同じフォルダに存在すること (KurenaiEngineLibraryのPostBuildEventがWindows SDKからコピーするため、 プロジェクト参照の構成であれば自動的に揃う)。DX12のシェーダーはこのdxcで シェーダーモデル6.5へコンパイルされる(4.2.2節参照)

一方KurenaiPacker.exe(Tools\KurenaiPacker\KurenaiPacker.vcxproj)は assimp・DirectXTexに加えKurenaiEngineLibrary.vcxprojへの依存を持つ (RHI::TextureImageによるBC7圧縮を利用するため)。アセットを.gltf/ .fbxから.kmodelへ変換する場合のみビルド・実行が必要で、詳細な ビルド手順・コマンドラインはREADME.mdを参照。

ポイント/スポットライトの影シャドウマップもレイトレーシングも平行光1灯のみ対応。ポイント/スポットライトの影はスクリーンスペースシャドウ(深度バッファのレイマーチ)でのみ得られる
レイトレーシングAO/GIの間接光バウンス面が画面に映っていればすべてのライトの寄与(影付き)を拾えるが、画面外・手前の面に隠れた面では太陽の直接光だけの簡略計算になり、色もマテリアルの定数値になる。またレイの最大距離より遠い面は遮蔽物にも間接光の光源にもならない
レイトレーシングシャドウの適用範囲不透明サーフェス(G-Buffer)の直接光パスだけを置き換える。半透明の描画と反射プローブのキャプチャはカメラ視点の画面空間バッファを使えないため、レイトレーシングを選んでいる間もカスケードシャドウマップを描き続けてそちらを使う
ライトの同時描画数最大1024灯まで(実データでの想定はせいぜい数灯〜十数灯)。超過分はカメラに近い順に採用される
