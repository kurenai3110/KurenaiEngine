# 性能の測り方

**「速くなった」は事実の主張である。** 測り方を決めてから測り、報告の前に検算する。

## 0. 測る前に決めること

| 決めるもの | 注意 |
|---|---|
| 構成 | **Release。** Debugの値は比較にならない(`docs/ImplementationHistory.md` にはDebugの計測値も残っているので、過去と比べるときは構成を確認する) |
| 実機 | **この開発機は RTX 4070 Ti(DXR Tier 1.1対応)。** `~/.claude/CLAUDE.md` にある基準実機 Intel UHD Graphics 620 は**別のPC**で、こちらでは再現しない |
| バックエンド | DX11(既定) / DX12(`-dx12`)。**経路が違えば別の測定**。RT反射やメッシュレットはDX12側にしか無い |
| シーンとカメラ | `-scene <名前>`。**カメラ位置で結論が変わる**(街路と俯瞰で差の向きが逆になった実測がある) |
| 解像度・アップスケール | 内部解像度が変わると比較にならない |
| TAA | ジッタを止めたいなら `-taa 0` |

**測る前に、そのシーンが仮説を区別できるか確かめる。** 効き量が小さい場面で測っても、
差はノイズに埋もれる。

## 1. 計測の入口は2つ。用途が違う

### `-perfdump <パス>` / `-perfdumpframes <枚数>` —— 計測専用

- **180フレームのウォームアップ後**(内部解像度の切り替えとストリーミングが片付くまで)、
  指定枚数ぶんの**全パスを閾値なしで平均**してCSVへ書く。既定は120フレーム
- CSVは `pass,avg_ms` の2列 + 最後に `__frames,<実際に集めた枚数>`
- 出典: `Samples/Sample3D/Source/Main.cpp` の `-perfdump` 解析と
  `KurenaiEngine/Source/Engine/KurenaiEngine3D.cpp` の書き出し

**平均しか出ない。** 分布(中央値・ヒッチ)が要るなら、この経路では取れない。

### `Perf` ログ —— 常時の様子見。**測定には使わない**

- 1秒ごとに1行。本体行(`FPS / CPU / GPU / GPU待ち / 最悪フレーム`)はその1秒の平均
- **`GPU内訳[ms]` は集計期間の最後の1フレームぶんだけ**で、**0.05ms未満のパスは落ちる**
- 数値を報告するためにこれを読まない。読むのは「今どの経路で走っているか」の確認

## 2. 信用できる測り方

- **パス別のGPU時間を原因の帰属に使わない。** 直後のリソース遷移による待ちを吸うため、
  「1534スレッドの判定に1ms」のようなありえない値になる。
  **UIのトグルで機能をON/OFFして総GPU時間の差を見るのが唯一信用できる**
  (根拠: `docs/ImplementationDetail.md` 47.12節)
- **FPSは回帰の指標にならない。** フレームレート制限で飽和する。
  同じ実行内でGPU時間が3倍違ってもFPSは56.6〜56.8で動かなかった実測がある
- **トグルを切り替えたら1秒以上あけてから測る。** ログのサンプル周期が1秒なので、
  切り替え直後の行は前の状態を含む
- **対照を取る。** A/Bの前に「何も変えずに2回」測り、**ノイズ下限**を出しておく。
  それより小さい差は差ではない

## 3. 代表値と外れ値

- **中央値を使う。** 平均はファイアフライ的な外れフレームに引っ張られる
- ヒッチを捨てるなら基準を書く(実測では `GPU待ち` が 0.5ms を超えた行を捨てている)。
  **捨てる割合が条件間で揃っていないなら、捨てない場合も併記する**
  (街路27〜36% / 俯瞰7〜21%と偏った実例がある)
- 分布を1つの数へ畳む前に、**どちら側が縛るのか**を決める。
  最悪フレームが問題なのか、定常のコストが問題なのかで代表値が変わる

## 4. 測定を壊すもの

- **別worktreeの同名exeが同時に走っていると、GPUを取り合って値が壊れる。**
  これを撮影方法(`PrintWindow`)のせいだと誤って断定した事例がある。
  測る前に**自分が起動したPID以外の同名プロセスが無いか確認する**
  (プロセスは必ずPIDで扱う。名前指定の終了は禁止)
- **Releaseにデバッグレイヤーは無い。** 性能ログに「エラー0件」と出ていても、
  D3D12のAPI誤用を検証したことにはならない
- 起動直後は内部解像度の切り替えとストリーミングが走っている。整定を待つ

## 5. カウンタを読むとき

- **単位を確かめる。** カリングの統計を「モデル数」と読んで2倍外した実例がある
  (1インスタンスがG-Bufferと深度プリパスの2区画へ積まれるため、当時のログは候補件数だった)。
  **既知の数で割り切れないか**を見る
- **絵が変わらない最適化は、数値でしか確かめられない。** 保守的なカリングが効いているかは
  間引き数で見る。ただし**間引き数からは経路が切り替わったかは分からない**
  (カメラが止まっていれば新旧で同じ数が出る)。経路そのものはログの該当行で確認する

## 6. 報告

- **どの実機・どのバックエンド・どのシーンとカメラ・どの構成・どの解像度**かを必ず添える。
  これが無い数値は再現できない
- 根拠と導出は `docs/ImplementationDetail.md`、経緯は `docs/ImplementationHistory.md`
- **報告の前に `double-check`。** 測った数値・「遅くなっていない」・原因の断定は
  重い主張なので、`verifier` と Codex の**2系統**に当てる(線引きは `double-check` 2節)
