# シェーダの不具合を数値で切り分ける

**`shader-check` は入口、`ab-compare` は出口、これはその間。**

| 症状 | スキル |
|---|---|
| HLSLが通るか知りたい | `shader-check`(通常はビルドが兼ねる) |
| 変更前後で最終画面がどう違うかを言い切りたい | `ab-compare` |
| **コンパイルは通っているのに絵が違う。どこで壊れたか分からない** | **これ** |

`ab-compare` の対照実験の作法(1〜3節)はここでも前提。書き写さないので、必要なら開くこと。

## 0. 始める前に決める

- 症状を「**どのバッファの、どの画素の、どの成分が、期待からどれだけずれているか**」へ書き換える。
  書き換えられないなら、まだ測る段階ではない。段1へ行って範囲を半分にする
- **仮説を先に3つ書く。** 1つしか書かないと、それを潰せなかったときに消去法になる
- **期待値を先に書く。** 測ってから期待値を決めると必ず合う

## 1. 手順の並び(安い順・確実な順)

| 段 | 手 | コスト | 分かること |
|---|---|---|---|
| 0 | ログを読む | 秒 | 経路が選ばれているか、どのバリアントが焼けたか |
| 1 | `-debugview N` で該当バッファを表示して撮る | 分 | どのパスまで正常か(**範囲を半分にする**) |
| 2 | `-dumptex` + `stat` | 分 | 定数化・全ゼロ・NaN・範囲逸脱。**目視で見えないものがここで出る** |
| 3 | `where` / `px` / `rect` / `row` / `hist` | 分 | 壊れている**場所の座標**と、条件付きの破綻 |
| 4 | シェーダに定数を焼き込んで上流を迂回 | ビルド1回 | **受け渡しが切れているのか、式が違うのか** |
| 5 | 実行時の値を数個ログに出す | ビルド1回 | 定数バッファ・CPU側の値 |
| 6 | 式をPythonで再実装して真値と比べる | 時間 | 式そのものが間違っているか |
| 7 | RenderDoc | 高 | バインドの取り違え(**値のダンプでは分からない種類**)。**ただし現状は手動のみ**(下記) |

**降りる前に、前の段で分かったことを1行書き残す。** これをやらないと後で消去法に戻る。

## 2. 状態を固定する(省略するとこれ以降が全部無意味)

```
Sample3D.exe -dx12 -scene <名前> -taa 0 -debugview <番号>
```

- **UI操作に依存させない。** つまみで切り替えると再現性が落ちる
- **`-taa 0` を付ける。** TAAのジッタは投影行列を毎フレームずらすので、同じ条件で2回撮っても
  ダンプがビット一致しない。まず再現性の下限をゼロにする
- **同一条件2回でビット一致を確認する。** floatのダンプなのでビット一致が期待値。
  一致しないなら、そこに理由がある(時間項・ジッタ・蓄積)
- 自動露出(EV100)はシーンを跨いで引き継がれる。A/Bは必ず起動直後から同じ手順で
- **Debugビルドで一度起動して `D3D12DebugLayer` タグを読む。** リソース状態遷移や
  ディスクリプタの取り違えはここにしか出ない。**Releaseではデバッグレイヤは動かない**
- Debugのシェーダは `-Od` で焼かれる。**Releaseでだけ出る破綻はDebugで再現しないことがある**

## 3. 段0 — ログ

`Samples/Sample3D/Build/Bin/x64/<構成>/KurenaiEngine_DX{11,12}.log`
(**worktreeで作業中は自分の出力フォルダのものを見る**)。

| 見るもの | 何が分かるか |
|---|---|
| 先頭のGPU名と DXR / メッシュシェーダー / bindless の対応 | その機能が実機で走りうるか |
| 「事前コンパイル済みシェーダー: ...」 | SM 6.6 / 6.5 / 5.0 のどれで動いているか |
| `D3D12DebugLayer` タグ(Debugのみ) | API誤用。**絵に出ない壊れ方はここにだけ出る** |
| `Perf` タグ | パスが実際に走っているか(時間が出ていなければ走っていない) |

「そのパスが走っているか」は**最初に確かめる**。走っていないバッファの中身は前フレームの
残骸か未初期化で、それを見て原因を考えると丸ごと外す。

## 4. 段1 — `-debugview` で範囲を半分にする

番号の並びは `KurenaiEngine3D.h` の `enum class DebugView` の順。名前は
`Source/Engine/UI/DebugViewPanel.cpp` の表示名配列。**片方だけ見ない**(同ファイルの
`static_assert` が並びの一致を要求している)。

- 値そのものを見たい番号: `DepthRaw` / `SceneColorRaw` / `AOIndirectLightRaw` / `AOOcclusionRaw`
- **Gainを上げないと真っ黒なバッファがある。** 間接拡散光は暗い室内で 0.02〜0.1 程度
- **パスが走っていないフレームでは前フレーム/未定義の残骸が見える番号がある**
  (`SoftwareRaster*` / `MegaLights*`)。「壊れている」と読む前に段0へ戻る
- **深度はReverse-Z。** 近が1.0、背景(ジオメトリ無し)が0。逆に書いても絵は出る
- **シャドウマップだけは通常深度。** 1.0クリアで、最遠が1.0

ここは「どのパスまで正常か」を絞るために見るところで、**判定には使わない。**

## 5. 段2 — `-dumptex` で線形の生値を落とす

```
Sample3D.exe -dx12 -scene MaterialTest -taa 0 -dumpframe 200 -exitafterdump ^
  -dumptex GBufferNormal C:\...\normal.bin ^
  -dumptex GBufferDepth  C:\...\depth.bin ^
  -dumptex ShadowCascadeArray C:\...\shadow1.bin -dumptexslice 1 ^
  -dumptex HiZTexture C:\...\hiz2.bin -dumptexmip 2
```

| オプション | 意味 |
|---|---|
| `-dumptex <名前> <パス>` | **繰り返し可**。1回の起動で複数枚を同じフレームから落とす |
| `-dumptexmip <N>` / `-dumptexslice <N>` | **直前の** `-dumptex` に掛かる(既定0) |
| `-dumpframe <N>` | 何フレーム目で撮るか。既定180 |
| `-exitafterdump` | 書き終えたら自動終了 |
| `-taa <0/1>` | TAAの有無 |

- **指定できる名前を知りたいときは、わざと存在しない名前を渡す。**
  有効な名前が全部エラーログに並ぶ(UIを見なくても分かるようにしてある)
- **アプリをループで起動しない。1回の起動で必要なバッファを全部吸う**(`verify-app` 0節)
- **ログの「テクスチャを書き出しました」を待ってから読む。**
  ファイルが存在することは書き終わりを意味しない
- **`-dumpframe` を小さくしすぎない。** 起動直後はストリーミングが走っている途中で、
  シーンが `RenderResolution` を持つ場合は内部解像度も既定値(1920x1080)から切り替わる。
  待たずに撮ると読み込み途中の絵や別の解像度の絵を掴む
- 名前は `m_` を外したメンバ名。増やすときは `KurenaiEngine3D::BuildDumpableTextureTable`
- Texture3D(雲のノイズ)とBC圧縮のアセットテクスチャは非対応。エラーログを出して断る

## 6. 段2〜3 — `Tools/texdump_inspect.py` の読み方

```
python Tools/texdump_inspect.py selftest              # まずこれを通す
python Tools/texdump_inspect.py stat  <dump.bin>
python Tools/texdump_inspect.py where <dump.bin> --pred nan
python Tools/texdump_inspect.py diff  <a.bin> <b.bin>
```

**`selftest` を通してから使う。** 自分で作った物差しで自分の成果を測ると、
物差しの誤りに気づけない。

`stat` で最初に見るもの、上から順に:

1. **`!! 定数化`の行** —— 全画素が同じ値。**値の受け渡しが切れる型のバグはここで一発で出る。**
   上流が書いていない / バインドが違う / 定数を焼き込んだまま
2. **`==0` の列** —— 背景とジオメトリの境目。**別のバッファの `==0` と数が一致するか**を見る。
   G-Bufferのアルベド・法線・深度は同じジオメトリマスクを持つはずで、
   フォーマットも型も違う3枚でこの数が揃えば、読み出しそのものは正しい
3. **非有限の行** —— NaN/Infは0件でも刷られる。「出ていない」と「見ていない」は別のこと
4. **`<0` の列** —— 符号なしフォーマットに負が出たら、読み方かエンコードが違う
5. **`len3`** —— 法線なら1.0付近のはず

件数には必ず母数が付く。**「何本のうち何本か」を数えるまで網羅性を語らない。**

`diff` は**符号の内訳**と**チャンネル別の平均差**を常に出す。

- 符号が片側に偏っていたら系統差。**「暗くする向きにしか働けない候補」は明るい側へ偏った差の
  主因ではありえない** —— 消去法を使わずに候補を落とせる
- 両側に散っていて、大きさが量子化の刻み未満ならULP(コンパイラのコード生成差)
- **「1ビットも動いていない」と出たチャンネル**は、変えたつもりが効いていない
- **差がゼロは合格ではない。** 「片方が実行されていない」を先に潰す(下の7節)

## 7. 対照実験(これ無しに結論を書かない)

| 何を示すか | どうやるか |
|---|---|
| 物差しが動いている | `selftest` が全件PASS |
| 再現性の下限がゼロ | 同一条件で2回起動してダンプを `diff`。ビット一致が期待値 |
| **その引数が効いている** | 値を変えて `diff` に差が出ることを示す(下記) |
| 差を変更に帰属できる | 項を1つだけ入れ替えて撮り比べる |

**「引数が効いている」の確認を飛ばさない。** 例えば `-dumptexslice 0` と `1` の結果が
ビット一致したとき、それは「両スライスが同じ」かもしれないし「sliceが無視されている」かも
しれない。**中身が違うと分かっているデータで一度差を出しておく**まで、
一致を根拠に使ってはいけない。

## 7.5 そのシーンは仮説を区別できるか(先に確かめる)

**測る前に、「2つの仮説がこのシーンでは同じ数値を出す」形になっていないかを見る。**
なっていたら、どれだけ精度よく当てはめても答えは決まらない。実測で2回踏んだ:

| 何が起きたか | なぜ区別できないか |
|---|---|
| 「法線の y を反転」と「光の向きを反転」を取り違えた | **光源がほぼ真上**だったため、`N·L = -N.y` となり両者が拡散項で数学的に同じになる。相対RMS 0.0004 で当てはまっても、正解ではなかった |
| 「ラフネスの閾値で壊れる」を、画面位置の条件と分離できなかった | `MaterialTest` は `roughness = i/(球数-1)` で球を**1列に**並べる。**ラフネスと x 座標が完全に相関**しており、「粗い2球」は同時に「左端の2球」でもある |

- **条件付きの破綻を追うときは、条件のパラメータと画面位置の相関を切ったシーンを使う**
  (並びを変える・別のシーンでも再現するかを見る)
- **光源の向きが軸に平行なシーンは、符号の取り違えを隠す。** 斜めから当たるシーンで撮り直す
- **当てはまりが良いことは、試していない仮説を否定しない。** 候補を列挙するとき、
  「符号の反転」なら *どの量の* 符号かを漏れなく数える(法線 / 光 / 接空間 / UV / 深度)

## 7.6 段7 — RenderDoc(値のダンプでは分からないものを見る)

**「値は正しいのに絵が違う」ときは、値ではなくバインドを疑う。**
どのドローがどのリソースを読み書きしたかは `-dumptex` では原理的に分からない。

`Tools/renderdoc_probe.py` が **GUI無しで**扱う(`qrenderdoc.exe` を起動しない)。

**このPC用のモジュールが要る。** 配布版のRenderDocには入っていないので、一度だけ:

```
powershell -NoProfile -ExecutionPolicy Bypass -File Tools\renderdoc_setup.ps1
```

置き場所も環境変数もスクリプトが決める(既定は `%LOCALAPPDATA%\KurenaiEngine\renderdoc`)。
**ビルドに使ったPythonでしか読めない**ので、実行はそのバージョンで行うこと
(スクリプトが最後に表示する)。根拠は `docs/ImplementationDetail.md` 63.10。

```
py -3.7 Tools/renderdoc_probe.py capture  --exe <Sample3D.exe> --frame 200 --out <dir> ^
                                          --args "-dx12 -scene MaterialTest -taa 0 ..."
py -3.7 Tools/renderdoc_probe.py actions  <capture.rdc>            # ドロー/ディスパッチの一覧
py -3.7 Tools/renderdoc_probe.py binds    <capture.rdc> --event N  # そのドローのバインド
py -3.7 Tools/renderdoc_probe.py textures <capture.rdc>            # テクスチャの一覧
py -3.7 Tools/renderdoc_probe.py export   <capture.rdc> --resource GBufferAlbedo --out x.bin
```

- **`capture` は撮るフレームを予約する**(`QueueCapture`)。ホットキーに頼らないので
  対象が決定的に決まる。`-exitafterdump` を併用すればアプリは自分で閉じる。
  **`-dumptex` と同じ起動で採れる**ので、1回の起動で両方の経路の値が手に入る
- **`export` は KTXD v2 で書き出す。** RenderDoc から採った値も `texdump_inspect.py` で測れる
- **リソースは `-dumptex` と同じ名前で出る**(`GBufferAlbedo` など)。
  `--resource` は名前でも `ResourceId::562` でも受ける。
  名前が出ないときはログの「グラフィックスデバッガ向けの名前を付けました: N本」を見る
  —— その機能が無効でテクスチャ自体が無いのか、表への追加漏れかを切り分けられる
- **`binds` が段7の本命。** 「どのドローが何を読み書きしたか」は値のダンプでは出ない。
  例: DirectLightingのドローで `Image index=5 ShadowCascadeArray` / `RTV[0] DirectLightTexture`
- キャプチャは数十〜数百MB。使い終わったら消す

**実測での裏取り**: 同じフレームの `GBufferAlbedo` を、RenderDocのリプレイと
エンジンの `-dumptex` の両方から取ると **3,686,400バイトが1ビットも違わない。**
別実装の2経路が一致したので、どちらも信用してよい。

## 8. 段4 — シェーダへの計装(3つの型)

1. **定数を焼き込んで上流を迂回する** —— G-Bufferや定数バッファを飛ばして値を直接与える。
   これで直れば受け渡しの問題、直らなければ式かライティング側
2. **中間値を出力チャンネルへ差し込む** —— ただし
   **「未使用に見えるaチャンネル」を使わない。** 読み手が居る
   (`GBufferMaterial.a` は水面のマテリアルID)。専用のデバッグ用RTを足すほうが安全
3. **分岐を潰す** —— `if` を片側に固定して、条件が原因か本体が原因かを分ける

いずれも**ビルドが要る**(`.hlsl` は `.kshader` へ焼かれ、出力フォルダに `.hlsl` は置かれない)。
**焼き直しが走ったことをビルドログで確認する**(「焼き直し: N / M ファイル」の行)。
「すべて最新です」なら AもBも同じシェーダで撮っている。

**`.kshader` のバイト比較で「シェーダが変わっていない」を示してはいけない。**
**焼き直しはバイト再現的ではない** —— ソースを1文字も変えずに `--force` で焼き直すと、
実測で **48本中37本の中身が変わる**。「変わっていない」を示したいなら、
`.hlsl` の `git diff` が空であることを見るか、DXILを束縛先で正規化してから比べること。

戻し忘れ対策: `git stash` して同じ手順で基準を撮り直す型を使い、終わりに
`git status --porcelain` と `git diff --stat` が空であることを確認する。
**ソースを戻してもビルド出力(`.kshader`)が戻っている保証は無い** ので、
戻したあとにダンプを取り直して基準とビット一致することまで見る。

## 9. 段5〜7

- **段5: 実行時の値を数個ログに出す。** 分岐フラグと実効値を数行出せば一発で決まる。
  仮説を1つずつビルドして潰すより速い(DX12の水面に映らない件は、これで決着した)
- **段6: 式をPythonで再実装して真値と比べる。** 写し間違いを先に潰すため、
  入力を1点だけ実測値に固定して両者を突き合わせてから全体を掃く
- **段7: RenderDoc。** バインドの取り違え(どのドローがどのリソースを読み書きしたか)は
  値のダンプでは**原理的に分からない**ので、ここでしか取れない情報がある。
  **GUI無しで動く**(`Tools/renderdoc_probe.py`。下の7.6節)

**シェーダの入力データを疑うのは、シェーダを疑うのと同じくらい早い段階でやる。**
`.kmodel` / `.kgeom` は `Tools/kmodel_inspect.py` で直接読める。
PLATEAUの頂点法線が全部 `(0,1,0)` だった件は、シェーダを3回疑ったあとに
データを直接読んで決着した。

## 10. 症状 → 最短経路

| 症状 | 最初に打つもの |
|---|---|
| 真っ黒 / 真っ白 | `stat`。`!! 定数化` と `==0` の列。段2で終わることが多い |
| まだらの穴・ホタル | `where --pred nan` / `--pred inf`、`hist --log` |
| 全体に明るすぎ/暗すぎ | `diff` の符号の内訳と分位点。定数倍か加算かは `--rel` で分かれる |
| 左右・上下が逆、傾きが逆 | `png --mode signed`、対称な2行で `row` を取って突き合わせる |
| **特定のマテリアル/距離でだけ壊れる** | **`--rect` で切って `stat` を2つ。** 全画面統計は条件付きの破綻を薄めて消す |
| DX11で出てDX12で出ない(逆も) | 両方でダンプして `diff`。バリアント(SM5.0/6.5/6.6)の違いを先に疑う |
| 前フレームの残骸に見える | 段0へ戻る。パスが走ったかをログで確認 |
| 陰影が付いていない | **陰(面の向き)と影(遮蔽)は別物。** `GBufferNormal` の `stat` で `!! 定数化` を先に見る |

## 11. やってはいけない失敗の型(どれも実測で記録されている)

- **目視で気づこうとする。** 絵を見るのは範囲を半分にするときだけで、判定には使わない
- **消去法で原因を帰属する。** 候補を2つ潰しただけで残りに帰属しない。項を1つずつ止める
- **「測れていない」と「実装が間違っている」を取り違える。** 物差しを先に既知の例へ当てる
- **物差しの網羅性を数えない。** 「差なし」と言う前に、何本のうち何本を通したかを数える
- **差分ゼロを合格と読む。** 逆向きの対照を先に取る
- **差の「画素数」だけで壊れ具合を測る。** `SceneColor` は fp16 の1〜2 ULP の差だけで
  差分画素数が 32,000〜231,000 まで振れる(実測)。**必ず値の大きさ(分位点)と一緒に読む**
- **「そこは変えていないから無改変のはず」と仮定する。** SSILは `DirectLightTexture` を読むので、
  **直接光を変えると間接光も変わる**(実測で間接光が58%まで落ちた)。
  依存を確かめずに「このバッファは無傷」と決めない
- **仮説を1つずつビルドして潰す。** 値をログに出すほうが速い
- **計装を戻し忘れる**

## 12. 終わり方

1. 直したら**元の症状を同じコマンドで測り直す。** 数値で戻ったことを見る
2. 計装の残骸を数える(`git status --porcelain` / `git diff --stat`)。ビルドが通ることを確認する
3. **数値・「壊していない」・原因の断定を報告する前に `double-check`**
4. 書き分ける: 根拠は `docs/ImplementationDetail.md`、経緯は `docs/ImplementationHistory.md`

## 関連

- 起動・撮影・PIDの扱い: `verify-app`
- ビルドと出力先: `build-run`
- HLSLの一括コンパイル検証: `shader-check`
- 最終画面のA/B比較: `ab-compare`
- 報告前の検算: `double-check`
